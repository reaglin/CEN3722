1 Introduction to AI Coding Assistants in HCI

The practice of designing human-computer interfaces has always evolved alongside the tools available to practitioners. Just as the introduction of visual design software transformed how interfaces were sketched and prototyped, and just as component libraries and CSS frameworks accelerated front-end development, AI coding assistants now represent a significant shift in how designers and developers translate ideas into working interfaces. Understanding what these tools are, how they work, and where they fit within the broader HCI design process is essential groundwork for anyone entering this space.

What Are AI Coding Assistants?

AI coding assistants are software tools powered by large language models (LLMs) — neural networks trained on enormous collections of text, code repositories, documentation, Stack Overflow threads, open-source projects, and more. Because these models have been exposed to vast amounts of code across many languages, frameworks, and problem domains, they develop a probabilistic understanding of programming patterns, conventions, and idioms. This is not rule-based knowledge like a linter or syntax checker; it is something more fluid — a capacity to reason about code in context and generate plausible continuations or alternatives.

The way you interact with an AI coding assistant is flexible. You can provide:

  • Natural language descriptions — for example, typing a comment like "Create a responsive navigation bar that collapses into a hamburger menu on mobile" and having the assistant generate the corresponding HTML, CSS, and JavaScript.
  • Existing code — pasting in a partially written component and asking the assistant to complete it, refactor it, or extend it with new functionality.
  • A combination of both — surrounding existing code with inline comments or prompts to guide the assistant toward a specific transformation or addition.

The outputs these tools can produce are varied and genuinely useful for HCI work. A single prompt might yield a fully written utility function, a boilerplate React component with appropriate props and state management, a suite of unit tests, or explanatory inline comments that document the logic of existing code. This breadth means AI assistants function less like autocomplete and more like a knowledgeable collaborator who can draft, explain, and iterate on code on demand.

These tools are not confined to one environment. They are integrated into IDEs like Visual Studio Code and JetBrains products, available in terminal-based agentic workflows, and accessible through browser-based platforms and APIs. This ubiquity means a designer working in a low-code environment and a software engineer deep in a complex codebase can both leverage similar underlying capabilities.

Key Tools: Claude Code, GitHub Copilot, and Codex

While the ecosystem of AI coding assistants is growing rapidly, three tools have become particularly relevant benchmarks for understanding what is currently possible.

GitHub Copilot is arguably the most widely adopted AI coding assistant in professional development contexts. It integrates directly into IDEs — most prominently Visual Studio Code — and provides real-time inline suggestions as you type. It watches the code you are writing, the file you are in, and often the broader project context, and offers ghost-text completions that you can accept, dismiss, or partially accept. For HCI practitioners, this means Copilot can suggest component structures, event handlers, and CSS patterns without breaking your flow. Because it is embedded in the editor, the feedback loop is immediate: you write, it suggests, you refine.

OpenAI Codex is accessible primarily via API rather than as a consumer-facing IDE plugin. It is the underlying model that has powered a range of developer tools, and its API access makes it particularly valuable for teams building custom tooling — for example, a design team that wants to build an internal tool that takes a Figma component description and generates a corresponding React component automatically. Codex's flexibility at the API level means it can be embedded into bespoke workflows that off-the-shelf tools cannot accommodate.

Claude Code, developed by Anthropic, is designed with a particular emphasis on agentic, multi-step tasks. Where Copilot excels at line-by-line or function-level suggestions and Codex shines in single-request API workflows, Claude Code is built to maintain coherent reasoning across longer, more complex sessions. This makes it especially well-suited for HCI projects that involve large codebases — for instance, refactoring an entire design system to meet updated accessibility standards, or methodically implementing a complex multi-step form with branching logic across many interconnected components. Claude Code's larger context window allows it to hold more of the codebase in view at once, reducing the risk of generating suggestions that are locally plausible but globally inconsistent.

It is important to recognize that these tools are not interchangeable. They differ in meaningful ways:

  • Context window size — how much code and documentation the model can consider simultaneously. Larger context windows allow for more consistent suggestions across a big project.
  • Integration method — whether the tool lives in your IDE, runs as an agent in a terminal, or is called via API determines how naturally it fits into your workflow.
  • Handling of design-related code — tools differ in how well they understand domain-specific frameworks like React, Vue, or SwiftUI, and in how reliably they produce accessible markup, valid ARIA roles, and semantically correct HTML.

The Role of AI in the HCI Pipeline

The HCI design process moves through several recognizable stages: research and discovery, ideation and conceptual design, prototyping, usability testing, and iterative refinement. AI coding assistants do not contribute equally at all stages, and understanding where they are most impactful helps practitioners use them strategically rather than indiscriminately.

The stages where AI assistants offer the most concrete value are prototyping and iterative refinement. During prototyping, speed matters: you need to translate a wireframe or design mockup into an interactive artifact quickly enough that you can test it with real users before too many assumptions calcify into decisions. An AI assistant can generate the scaffold of a UI component — its structure, basic styling, and state logic — in seconds, allowing a designer-developer to spend their time on the higher-level questions of interaction design rather than boilerplate code.

Consider a concrete example: a designer has a wireframe for a modal dialog that contains a multi-step form. Rather than hand-writing the component from scratch, they can describe it to an AI assistant: "Generate a React component for a multi-step modal with three steps: personal information, address details, and confirmation. Include progress indicators and validation before advancing to the next step." The assistant produces a working scaffold. The designer can immediately render it in the browser, interact with it, and identify what feels wrong — the transition between steps is too abrupt, the validation error messages are not descriptive enough, the progress indicator does not clearly convey which step is active. These are the real HCI questions, and the AI has cleared the path to asking them faster.

AI tools are also increasingly useful for generating accessibility markup. Proper use of ARIA (Accessible Rich Internet Applications) attributes, semantic HTML elements, focus management, and keyboard navigation is notoriously easy to get wrong or skip under deadline pressure. An AI assistant prompted to generate an accessible dropdown menu or a tab panel will typically include appropriate ARIA roles (role="tablist", role="tab", aria-selected), keyboard event handlers, and focus management logic. This does not eliminate the need for accessibility auditing, but it can meaningfully raise the baseline quality of generated code.

Where AI assistants are less useful is at the stages that depend on genuine human understanding of users and context. User research — interviews, observations, diary studies — requires interpretation, empathy, and judgment about what users mean when they behave in unexpected ways or express contradictory preferences. No AI assistant can sit with a frustrated elderly user navigating a healthcare portal and understand the emotional texture of that experience in the way a trained researcher can. Similarly, the high-level design decisions that follow from research — what the primary task flow should be, which interaction model best fits users' mental models, how to balance competing stakeholder needs — require a quality of reasoning and value judgment that current AI tools do not reliably provide.

Opportunities and Limitations of AI-Assisted Design

The opportunities are real and significant. The most immediate benefit is the reduction of repetitive coding tasks. HCI and front-end development involve a great deal of structural repetition: setting up routing, wiring up form validation, writing media queries, scaffolding component hierarchies. These tasks are necessary but not intellectually demanding, and they consume time that could be spent on harder problems. When AI assistants handle this scaffolding work reliably, practitioners can redirect their attention to the interaction problems, the visual hierarchy decisions, and the user research synthesis that actually differentiates good interface design from mediocre interface design.

There is also an opportunity in democratization. Designers who are not primarily coders can use AI assistants to produce functional prototypes that would previously have required a developer's involvement. This can reduce handoff friction and keep design and engineering thinking integrated for longer in the development process.

However, the limitations deserve equal attention. A critical one is that generated code may not align with a team's design system or brand guidelines. Most design teams at any scale have established component libraries, naming conventions, spacing tokens, color systems, and interaction patterns. An AI assistant trained on public code will generate suggestions that reflect generic conventions — Bootstrap-style grids, Material Design-influenced components, standard CSS naming. Integrating these suggestions into a project with a bespoke design system requires significant reworking, and developers must be vigilant about not letting AI-generated code slowly erode design system consistency.

Accessibility presents a related risk. While AI assistants can generate accessible markup, they can also generate markup that looks accessible but is subtly wrong — incorrect ARIA roles, missing focus management, or reliance on color alone to convey state. Practitioners cannot simply trust that AI-generated code meets WCAG standards without verification.

A more subtle limitation involves training data bias. AI models learn from the code that exists publicly, and the code that exists publicly reflects historical patterns in interface design — which are not neutral. Certain design patterns dominate because they were popularized by influential platforms, not necessarily because they are optimal for all users. An AI assistant may consistently suggest interaction patterns that work well for sighted, non-disabled, technically fluent users on large screens because that is what the training data predominantly reflects. Practitioners working on interfaces for diverse populations — older adults, users with low literacy, people using assistive technologies — need to be especially alert to this tendency.

Finally, there is the concern about skill development. If a student or early-career designer consistently uses AI tools to generate code they do not fully understand, they may progress through projects without developing the foundational knowledge that would allow them to debug, adapt, or critically evaluate that code. This creates a fragile competence: work that looks complete until something unexpected breaks, at which point the practitioner lacks the understanding to diagnose or fix it. The most effective use of AI coding assistants tends to be by practitioners who already have enough foundational knowledge to read the generated code critically, ask good follow-up questions, and recognize when a suggestion is subtly wrong.

Taken together, these tools represent a genuinely powerful addition to the HCI practitioner's toolkit — but one that rewards thoughtful, critical engagement rather than passive delegation.
