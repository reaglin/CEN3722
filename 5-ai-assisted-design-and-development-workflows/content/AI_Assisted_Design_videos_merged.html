Introduction to AI Coding Assistants in HCI

Introduction

AI coding assistants are tools that use large language models to suggest, generate, explain, and refactor code directly inside a developer's editor or terminal. Current examples include GitHub Copilot, Claude Code, and OpenAI's Codex-family tools. They range from inline autocomplete that finishes the line you are typing, to chat interfaces that answer questions about your project, to agent modes that can plan and carry out multi-step tasks across several files.

In this course these tools matter because interface work is iterative: you sketch a layout, build a prototype, test it with users, and revise. An assistant that can scaffold a component, draft placeholder content, or convert a design description into working markup shortens the distance between an idea and something you can actually put in front of a user. That speed is only useful if you can judge what comes back — AI output can be plausible but wrong, inaccessible, inconsistent with your design system, or built on assumptions you never stated.

The videos below introduce the practical shape of these tools. As you watch, pay attention to three things: where in the workflow the assistant is invoked (inline, chat, or agent), how much context the human has to supply for the output to be useful, and what the presenter does to check the result before accepting it. Those three habits — invoke, specify, verify — are what you will carry into the rest of the module.

Effective Prompting Strategies for Design Tasks

Introduction

Working with an AI assistant on a design task is itself an interface problem. The prompt is the control surface: what you type determines what the system can do for you, and vague input produces generic, unusable output. In this topic we treat prompting as a skill with structure — giving the model role and context, stating the task and constraints, specifying the output format, and supplying examples when the format matters.

For interface work, prompts also need domain content. A prompt that asks for "a login screen" gets you a cliche; a prompt that names the target users, the platform, the design system tokens, the WCAG contrast and focus requirements, and the error states you must handle gets you something you can actually critique and refine. Refinement is the normal case, not a failure: you read the output, find where it drifted from your intent, and change one thing in the prompt to close that gap.

The three videos below move from practical technique to a research view of why prompting is harder than it looks. While watching, collect concrete patterns you can reuse — ways to supply context, to constrain output format, to ask the model to reason or to critique its own work — and note the failure modes: over-trusting a confident answer, changing many things at once between attempts, and assuming the model shares background knowledge you never stated.

AI-Accelerated Prototyping Workflows

Introduction

Prototyping has always been the heart of HCI practice: you sketch an idea, build something just real enough to test, and learn from how people react to it. What has changed is the cost of getting from a wireframe to something clickable. AI coding assistants and design-tool integrations can now take a rough layout, a screenshot, or a written description and produce working component code in minutes, which shifts the bottleneck from "can we build it?" to "should we build it this way?"

This topic walks through the practical side of that shift. You will look at how a low-fidelity scaffold becomes code, how to generate and reuse components rather than one-off screens, how to iterate on a prototype through conversation with an assistant, and how to fold these tools into a team's existing workflow without creating chaos. Throughout, keep the trade-off in view: speed is only valuable if the artifact you produce is still testable, accessible, and consistent with your design system.

As you watch, pay attention to three things. First, what the human provides as input — the prompt, the frame, the existing design tokens — because output quality tracks input specificity closely. Second, where the demonstrator stops and corrects the AI, since those moments show you the judgment the tool cannot supply. Third, what is missing from the generated result: states, error handling, keyboard focus, responsive behavior. Those gaps are exactly where your HCI training earns its keep.

Maintaining Design Quality in AI-Assisted Projects

Introduction

AI tools can produce interface layouts, copy, and working code in seconds, but speed is not the same as quality. This topic asks a harder question: once an AI has generated something, how do you decide whether it is actually good? Design quality in an AI-assisted project still rests on the same foundations you have used all semester — usability heuristics, accessibility standards, consistency, and fitness for the intended users and context — but the review process changes because the output arrives faster, in larger volumes, and without a human author who can explain their reasoning.

The subtopics walk through a practical review pipeline. You first define what "quality" means for your project, then apply heuristic evaluation to AI-generated screens, audit generated markup and code for accessibility problems (missing labels, poor contrast, broken focus order, non-semantic elements), and establish code review habits that treat AI output as a draft from an unfamiliar collaborator rather than a finished deliverable. Finally, you consider how to keep your own design intent intact, so that the product reflects deliberate decisions rather than whatever the model happened to produce.

The three videos below approach this from complementary angles: using language models to critique UI mockups, simulating users to surface usability feedback, and the broader practice of using an AI model as an evaluator. While watching, note what each approach can reliably catch, what it misses, and where a human designer's judgment is still required. Pay particular attention to how evaluation criteria are specified — vague prompts produce vague critiques, while criteria grounded in heuristics or guidelines produce feedback you can act on.

Ethical Considerations and Professional Responsibility

Introduction

Using AI tools to generate layouts, copy, or code is now a normal part of interface work, but it raises questions that a tool cannot answer for you. Who gets credit for a design that an assistant largely produced? What happens when training data encodes stereotypes that surface in generated images, personas, or default settings? Can you legally ship code or assets that a model reproduced from someone else's work? This topic looks at those questions and at the professional obligations that come with them: being transparent about how work was produced, checking outputs for bias and misrepresentation, respecting licensing, keeping your own skills sharp, and deploying AI responsibly in products real people will use.

These concerns are not abstract for HCI practitioners. The designer is usually the last human checkpoint between a model's output and a user's screen, so judgments about attribution, fairness, and appropriateness land on you. Professional codes in computing treat this as a duty of competence, not a matter of taste: you are responsible for what you ship, regardless of which tool produced the first draft.

The three talks below approach the problem from different angles — present-day harms and bias, the data behind generative models and the creators it draws from, and the effect of heavy AI use on your own thinking. While watching, keep notes on concrete practices you could adopt: what you would disclose on a project, what you would check before accepting a generated interface element, and where you would deliberately do the work yourself.
