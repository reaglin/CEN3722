Introduction

Finding accessibility problems is only half the work. This topic is about the other half: turning audit findings into concrete design corrections and then standardizing those corrections as reusable patterns. Instead of fixing one broken form or one trapped modal at a time, you build a small library of components — form fields, navigation, dialogs, tables and charts — that are accessible by default, so the same defect does not reappear on the next screen.

The subtopics move through the component types that generate the most accessibility complaints. Forms need programmatic labels, grouping, and error messaging that assistive technology can announce. Navigation needs predictable structure, skip links, and keyboard reachability. Modals and overlays need focus management, correct roles, and a reliable way to dismiss them. Data displays — tables and charts — need structure and text alternatives so information is not locked inside visual layout alone. Finally, these fixes need a home in your design workflow so accessibility is checked each iteration rather than bolted on at the end.

The three videos below are short, hands-on walkthroughs of three of these component families. While watching, pay attention to the distinction between what is visible and what is programmatically exposed: a label you can see is not the same as a label a screen reader can read. Note also which techniques rely on native HTML semantics and which require ARIA plus JavaScript, and keep track of the keyboard behavior being demonstrated so you can reuse it as a checklist when you revise your own prototypes.

How These Videos Support the Learning Outcomes

Together these videos move the module from recognition to repair. They put WCAG-aligned techniques for labeling, focus management, and data structure into practice (MO1) and show the specific barriers — unlabeled inputs, lost keyboard focus, structurally meaningless tables — that an audit of visual, motor, and cognitive access would surface (MO2). Most directly, each is a demonstration of modifying markup and behavior so a prototype meets accessibility standards, which is the core of applying inclusive design principles to real components (MO3). Seeing how small implementation choices determine whether a user can complete a form or escape a dialog also makes the human cost of exclusion concrete, supporting your ability to articulate the ethical and legal stakes of these decisions (MO4).
