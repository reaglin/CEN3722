Foundations of WCAG Guidelines

Introduction

The Web Content Accessibility Guidelines (WCAG) are the internationally recognized standard for making digital content usable by people with disabilities. Published by the World Wide Web Consortium (W3C), WCAG is organized around four principles — Perceivable, Operable, Understandable, and Robust (the POUR principles) — which break down into guidelines, and then into testable success criteria. Those criteria are grouped into three conformance levels: A (minimum), AA (the level most commonly required by law and policy), and AAA (the most demanding).

In this course, WCAG gives you a shared, checkable vocabulary for talking about interface quality. Instead of saying a design "feels hard to use," you can point to a specific success criterion — contrast, keyboard access, focus visibility, target size — and explain exactly what must change. This matters practically as well: WCAG 2.0, 2.1, and 2.2 AA are referenced by accessibility laws and procurement requirements in many countries, so knowing the structure and versions is part of professional competence.

As you watch the videos below, focus on three things: how a success criterion is worded and why that wording makes it testable, how the version numbers (2.0, 2.1, 2.2) build on one another rather than replacing one another, and how individual criteria map back to the POUR principles. Keep a running list of criteria you could actually check on an interface you have built — you will need that skill for the module assignments.

Accessible Color and Visual Design

Introduction

Visual design decisions that feel purely aesthetic — a brand color, a light gray caption, a thin typeface, a removed focus outline — can quietly make an interface unusable for people with low vision, color vision deficiency, or age-related sight changes. This topic looks at the visual layer of accessibility: how much contrast text and UI components need, why color alone cannot carry meaning, how typography choices affect readability, and how users who navigate by keyboard need to see where they are on the page.

These concerns are codified in the WCAG 2.1 success criteria you are studying in this module, most notably the contrast ratio thresholds for text and non-text content, the "use of color" criterion, and the requirements for visible focus. Knowing the numbers matters, but so does knowing how to measure them with real tools and how to fix a design without throwing away its visual identity.

As you watch, pay attention to three things: the specific ratio targets and what counts as large text, the workflow each presenter uses to test an existing screen, and the design moves they make when a color fails — adjusting lightness, adding an icon or text label, or changing the element rather than the palette. Try the same steps on an interface you use daily, or on your own prototype.

Screen Reader Compatibility

Introduction

Screen readers turn an interface into speech or braille, but they can only convey what the underlying code actually communicates. A heading that is merely large, bold text is just text to a screen reader; a heading marked up as a heading becomes a navigable structure a user can jump through. This topic looks at the layer beneath the visual design — semantic HTML elements, landmark roles, ARIA labels and descriptions, text alternatives for images and media, and announcements for content that changes after page load.

This matters in CEN3722 because interface design is not finished when it looks right. A prototype that passes a visual review can still be unusable for someone who is blind or has low vision if its structure is invisible to assistive technology. Learning to think in terms of roles, names, states, and reading order gives you a vocabulary for evaluating and repairing interfaces, and connects directly to WCAG success criteria you will apply later in the module.

The three videos below come from the same accessibility instructor and are best watched in order. As you watch, pay attention to one recurring theme: ARIA supplements semantic HTML, it does not replace it. Note which native HTML elements already carry accessibility information for free, when an ARIA attribute is genuinely needed, and how incorrect ARIA can make an interface worse than no ARIA at all. Keep a running list of the specific elements and attributes mentioned so you can check for them in your own prototypes.

Inclusive Design Principles Beyond WCAG

Introduction

Meeting WCAG success criteria is a floor, not a ceiling. Inclusive design asks a broader question: who is being left out by the choices we make, and how can an interface flex to accommodate the full range of human abilities, contexts, and preferences? This topic introduces the social model of disability — the idea that people are disabled by barriers in the environment rather than by their bodies or minds — and the design mindset that follows from it.

Four threads run through the material. The social model and inclusive mindset reframe accessibility as a design responsibility rather than a compliance checkbox. Cognitive accessibility focuses on memory load, attention, clear language, predictable structure, and giving users enough time. Responsive and adaptive design extends accessibility across screen sizes, zoom levels, input methods, and user settings. Animation and motion sensitivity cover the real harm that movement, auto-advancing content, and parallax effects can cause for users with vestibular disorders, migraine, or attention differences.

The three videos below come from the Web Accessibility For All series. As you watch, look for the pattern each one follows: a common design pattern is named, the specific users it excludes are identified, and a more inclusive alternative is proposed. Try to connect each example back to a WCAG criterion you already know, then notice where the recommendation goes beyond what the standard literally requires — that gap is where inclusive design lives.

Accessibility Auditing

Introduction

An accessibility audit is a systematic evaluation of an interface against a standard — usually WCAG 2.1 — to find, document, and prioritize barriers that keep people with disabilities from using a product. Auditing sits between knowing the guidelines and actually fixing things: it is the activity that turns an abstract success criterion like "non-text content has a text alternative" into a concrete, located, reproducible defect that someone on a team can repair.

In this course, auditing matters because it is how you check your own work. Automated checkers can flag perhaps a third of common issues, so a usable audit method combines tooling (browser extensions, DevTools panels, contrast checkers) with manual inspection (keyboard-only navigation, heading and landmark structure, focus order, form labels, meaningful alt text) and, where possible, testing with assistive technology. You will apply this to your own prototype, then decide what to fix first and how to write it up.

As you watch, pay attention to three things: the method each presenter uses to select pages and work through them in a repeatable order; the evidence they capture for each finding (location, standard violated, what the user experiences, suggested remediation); and the judgment calls about severity — which failures block a task entirely versus which degrade the experience. Notice also how the tools differ in purpose: WAVE surfaces page structure and flags for human review, DevTools digs into the accessibility tree and computed properties, and a formal audit report packages all of it for stakeholders.

Applying Corrective Design Patterns

Introduction

Finding accessibility problems is only half the work. This topic is about the other half: turning audit findings into concrete design corrections and then standardizing those corrections as reusable patterns. Instead of fixing one broken form or one trapped modal at a time, you build a small library of components — form fields, navigation, dialogs, tables and charts — that are accessible by default, so the same defect does not reappear on the next screen.

The subtopics move through the component types that generate the most accessibility complaints. Forms need programmatic labels, grouping, and error messaging that assistive technology can announce. Navigation needs predictable structure, skip links, and keyboard reachability. Modals and overlays need focus management, correct roles, and a reliable way to dismiss them. Data displays — tables and charts — need structure and text alternatives so information is not locked inside visual layout alone. Finally, these fixes need a home in your design workflow so accessibility is checked each iteration rather than bolted on at the end.

The three videos below are short, hands-on walkthroughs of three of these component families. While watching, pay attention to the distinction between what is visible and what is programmatically exposed: a label you can see is not the same as a label a screen reader can read. Note also which techniques rely on native HTML semantics and which require ARIA plus JavaScript, and keep track of the keyboard behavior being demonstrated so you can reuse it as a checklist when you revise your own prototypes.
