Introduction

Getting an app from "it works on my machine" to "it is live in a store" involves a set of concrete, checkable steps. A release build is not simply a debug build with a different name: it typically uses different signing credentials, different configuration values, optimization and shrinking settings, and often a different distribution format (for example an Android App Bundle rather than a plain APK). Before that build goes anywhere, it needs to be exercised against a pre-submission checklist — does it install cleanly on a fresh device, do permissions and accounts behave, do crash reports and analytics point at production endpoints, and does the interface still meet the usability and accessibility standards you have been applying all term?

Alongside the binary itself, stores expect a package of deliverables: a correctly incremented version number and build number, release notes that describe what changed, store listing metadata, screenshots, and any declarations the platform requires. Sloppy version numbering is one of the most common reasons an upload is rejected outright, and vague release notes slow down human review. Treating these artifacts as part of the deliverable — not as paperwork added at the last minute — is what separates a submission that moves through review from one that bounces back.

The three videos below approach this from different angles: build configuration on native Android, build configuration in a cross-platform workflow, and the tooling a store itself offers for testing and submission. While watching, pay attention to the distinction between debug and release configuration, to where version and build identifiers are declared, and to what each platform asks you to supply before it will accept an upload. Note also how much of this work can be automated once, then repeated for every release.

About this video

This Expo tutorial shows how to configure and produce a build using EAS (Expo Application Services), the hosted build service for Expo and React Native projects. It walks through the configuration steps needed to get a build generated by the service rather than on your own machine, which is the same pipeline teams typically use to produce store-ready binaries. The focus is on the configuration file and the practical setup sequence.

Why this video

It covers build configuration from a cross-platform perspective, which is useful if your interface project is not a native Android app, and it illustrates how a managed build service handles the credentials and settings that submission depends on.

How These Videos Support the Learning Outcomes

Together these videos move students from configuring a production build to handing it over to a store. The Android and Expo videos support MO2 by showing where release settings, credentials, and version identifiers are declared, so students can inspect their own projects and judge whether a build is genuinely release-ready rather than a renamed debug build. The Amazon Appstore session supports MO1 and MO3 by demonstrating, from the store's side, what testing and submission involve and what a developer is expected to upload — a concrete model students can carry over when assembling metadata, screenshots, release notes, and accessibility descriptions for the Apple App Store or Google Play.
