Development Environment Setup and Use

▶

Building a usable, testable prototype is not purely a design challenge — it is equally an engineering and operational challenge. Before the first line of prototype code is written, a team must make deliberate decisions about which tools they will use, how they will collaborate on the codebase, how they will work efficiently during the build phase, and how they will get the finished artifact into the hands of real test participants. Each of these concerns is interconnected: a poorly chosen technology stack can make rapid deployment difficult; a missing version-control discipline can cause the team to accidentally overwrite a working prototype hours before a test session; a local development workflow that no one has documented can leave a new team member unable to run the project at all. This topic addresses all four of these concerns as a unified body of professional practice.

Choosing an Appropriate Technology Stack

The most technically sophisticated stack is rarely the most appropriate one for a usability testing prototype. The fundamental goal of a prototype is to present realistic interaction patterns to test participants as quickly and reliably as possible — not to demonstrate engineering ambition. Stack selection should therefore be driven by three practical questions: What do we already know? What will deploy quickly? What do the test tasks actually require?

Choosing technologies the team already knows dramatically reduces the time spent debugging environment issues rather than building the prototype itself. If everyone on the team is comfortable with plain HTML, CSS, and vanilla JavaScript, that combination will almost always outperform a team struggling to configure a framework they learned last week. Frameworks like React, Vue, or Svelte can be excellent choices when the team is already proficient with them, but they introduce build pipelines, module bundlers, and dependency graphs that add friction when time is short.

The second criterion — support for rapid deployment to an accessible URL or device — rules out many architectures that would be entirely appropriate for a production system. A prototype does not need a containerized microservices backend. In the vast majority of usability test scenarios, the "backend" can be simulated with one of the following lightweight approaches:

  • Static HTML/CSS/JS sites — Require no server-side runtime at all. They can be hosted on GitHub Pages, Netlify, Vercel, or Cloudflare Pages in minutes, often with a single command or a push to a repository branch.
  • Mock APIs — Tools like json-server, MSW (Mock Service Worker), or hosted services like MockAPI.io let the prototype make realistic HTTP requests that return pre-scripted JSON, simulating real backend behaviour without building any server logic.
  • Local JSON data files — For prototypes that simply need to render lists, search results, or detail pages, a plain .json file fetched with the Fetch API is often sufficient. There is no database, no authentication layer, and no server to configure.

The third criterion is that the stack must support the specific interaction patterns the test tasks require. If a task asks participants to fill out a multi-step form with inline validation, the team needs to be able to implement client-side form logic. If a task involves filtering a product catalogue, the team needs the ability to manipulate and re-render a list. These requirements should be mapped explicitly to stack capabilities before the decision is made, not discovered mid-build.

A useful way to evaluate candidate stacks before committing is to score them against the criteria that matter most for the project:

Stack Option Team Familiarity Deploy Speed Supports Required Interactions Overall Fit
Plain HTML + CSS + Vanilla JS High Very Fast Moderate (sufficient for most tasks) Excellent for simple–moderate prototypes
React + json-server mock API Medium (if team knows React) Fast (with Vite or CRA) High (component-driven UI, state management) Good when team is React-proficient
Next.js + Vercel Medium–Low (SSR concepts) Fast (Vercel integration) High Overkill unless SSR behaviour must be tested
Full custom backend (Node/Express + database) Variable Slow (infrastructure setup) High Almost never justified for a test prototype

The takeaway from this analysis is almost always that simpler is better. A prototype that works reliably on a static hosting platform is worth far more to the research team than a sophisticated architecture that requires troubleshooting on the morning of a test session.

Setting Up Version Control

Version control is not an optional professional nicety — it is the single most important operational safeguard for a prototype project. Without it, the team has no reliable way to recover from mistakes, coordinate parallel work, or return to a known-good state before a test session. Git is the universal standard and should be initialized at the very beginning of the project, before any other files are created.

The foundational practice is to commit frequently and to write descriptive commit messages. A commit message like fix bug is nearly useless in a project history. A message like fix: validation error clears correctly on form step 2 allows any team member — including the original author a week later — to understand what changed and why. A widely used convention is the Conventional Commits format, which prefixes messages with a type such as feat:, fix:, chore:, or refactor:. This is not mandatory, but adopting any consistent convention is far better than having none.

Branching is the mechanism that allows multiple team members to build different features or flows in parallel without interfering with each other's work. A simple but effective branching strategy for a small prototype project looks like this:

  • main — Always contains the most recently verified, stable version of the prototype. Nothing is committed directly to main except through a reviewed merge.
  • Feature branches — Named after the feature or flow being built (e.g., feature/checkout-flow, feature/search-results-filter). Each developer works in their own branch and merges into main when the feature is complete and tested locally.
  • Fix branches — Short-lived branches for correcting specific bugs found during review or testing (e.g., fix/mobile-nav-overflow).

One of the most practically valuable version-control habits for prototype work is tagging release-ready commits. Before each test session, the team should create a Git tag that marks the exact state of the prototype that will be tested:

git tag -a v1.0-session1 -m "Prototype state for usability test session 1, 2024-11-15"
git push origin v1.0-session1

If a late-stage change introduced between sessions causes a critical failure, the team can immediately check out the tagged commit and redeploy it, rather than scrambling to diagnose and undo an unknown number of changes. This one practice has saved countless test sessions from preventable disaster.

Teams should also document their conventions in a short file — often called CONTRIBUTING.md — stored in the repository itself. This file should specify the branching model, commit message format, and any other project-specific norms. When a new team member joins, they can read this file and immediately understand how to participate in the workflow without relying on verbal handoffs.

Local Development and Live Preview Workflows

Working efficiently during the build phase requires a local development environment that reduces friction between making a change and seeing its effect. The most impactful capability is automatic browser refresh on file save, commonly called "hot reload" or "live reload." Without this, developers must manually switch to the browser and refresh after every change — a small friction that adds up to significant wasted time and broken concentration over a full day of work.

Most modern development toolchains include this capability out of the box. Some common examples:

  • Vite — Starts a local dev server with npm run dev and provides near-instant hot module replacement for React, Vue, Svelte, and plain JavaScript projects.
  • Parcel — Zero-configuration bundler that automatically serves files and refreshes the browser on save.
  • Live Server (VS Code extension) — The simplest possible option for plain HTML/CSS/JS projects; right-click an HTML file and select "Open with Live Server."
  • Browsersync — Particularly useful for testing across multiple devices simultaneously, as it synchronises scroll position and interactions across all connected browsers.

Cross-browser and cross-device testing should happen continuously throughout development, not as a single step at the very end. It is far easier to fix a layout that breaks on Safari or a tap target that is too small on mobile when the issue is discovered immediately after the relevant code is written. Discovering these issues the day before a test session means fixing them under time pressure, which invites new bugs. A practical habit is to open the prototype in at least two browsers (typically Chrome and Safari or Firefox) and at a mobile viewport size after completing each significant feature.

Browser developer tools are an essential part of the local development workflow and deserve deliberate attention. The key capabilities relevant to prototype development include:

  • Elements / Inspector panel — Allows real-time inspection and editing of the DOM and CSS. Invaluable for diagnosing layout issues without touching the source files.
  • Console — Displays JavaScript errors, warnings, and console.log() output. The first place to look when an interaction is not behaving as expected.
  • Network panel — Shows all HTTP requests made by the page, including requests to mock APIs or JSON files. Useful for confirming that data is being fetched correctly and for diagnosing failed requests.
  • Device toolbar / Responsive Design Mode — Simulates different screen sizes and pixel densities. Not a substitute for testing on real devices, but an efficient way to catch obvious layout problems early.
  • Performance and Accessibility panels — Less critical for prototype work but useful if the test tasks involve performance perception or if accessibility is an explicit research focus.

The local environment configuration must be documented. This means writing a README.md file that any team member can follow to get the project running from scratch on a new machine. At minimum, this documentation should specify: the required runtime versions (e.g., Node.js 20.x), the installation command (e.g., npm install), and the command to start the development server (e.g., npm run dev). If environment variables are needed, the README should list which variables are required and how to obtain values for them — never the actual secret values themselves. A team that can onboard a new contributor in under ten minutes from a documented README has solved a problem that many prototype teams ignore until it becomes urgent.

Deploying the Prototype for Testing

Deployment is the point at which the prototype transitions from a private development artifact to a live testing tool, and it introduces an entirely different class of risks. The most important principle of deployment is timing: the prototype should be deployed to its final testing URL significantly in advance of the first test session — ideally at least 24 to 48 hours ahead. This buffer allows time to discover and resolve environment-specific issues that do not appear during local development, such as broken asset paths, CORS errors when the domain changes, or missing environment variables on the hosting platform.

Before a test session, the deployed prototype must be validated against the same conditions participants will experience. This means:

  • Device types — If participants will use smartphones, the prototype must be tested on actual smartphones, not only in the browser's device simulator. Real devices expose issues with touch handling, font rendering, and viewport behaviour that simulators miss.
  • Network conditions — If participants will access the prototype over a home broadband connection or cellular data, testing only on a fast office network can produce false confidence. Tools like Chrome's network throttling option in the developer tools can simulate slower connections, and cloud-based testing platforms can test from real network locations.
  • Browsers — Know which browser participants will use (often specified in the recruitment screener) and validate the prototype in exactly that browser and version.

Any accounts, login credentials, or pre-populated test data required by the test tasks must be configured in the deployed environment before testing begins — not as an afterthought. If a task requires a participant to log in as a specific user and see a personalised dashboard, that user account and its associated data must exist and be in the correct state. If the same test account will be used across multiple sessions, the team must have a documented reset procedure that restores the account to its baseline state between sessions.

Perhaps the most commonly overlooked deployment practice is having a rollback plan. A rollback plan answers the question: if the deployed prototype breaks critically five minutes before a test session, what do we do? The answer should be specific and pre-tested, not improvised under pressure. A well-formed rollback plan might look like this:

  • The previous stable version is tagged in Git (e.g., v1.0-session2) and can be checked out immediately.
  • The deployment command to push that tagged version to the hosting platform is documented and verified to work.
  • One team member has the credentials and access necessary to trigger the deployment.
  • The team has estimated that the rollback process takes no more than five minutes, giving them a realistic option even close to session start time.

Popular static hosting platforms such as Netlify and Vercel provide built-in deployment history and one-click rollback to any previous deployment, which makes this plan trivial to execute. Teams using these platforms should familiarise themselves with the rollback interface before they need it urgently, not during a crisis.

The discipline of thorough deployment preparation reflects a broader principle: the prototype exists to serve the research, and the research cannot produce valid findings if the prototype fails during the session. Every practice described in this topic — from choosing an appropriate stack to having a documented rollback plan — is ultimately in service of the same goal: ensuring that when a participant sits down to complete a task, the prototype works exactly as intended.
