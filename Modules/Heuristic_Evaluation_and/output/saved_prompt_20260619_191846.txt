TOPIC 1: Introduction to Heuristic Evaluation
  • What Is Heuristic Evaluation?
  •   HE is an inspection method, not a user test — evaluators act as surrogates for end users.
  •   It is most effective when conducted by usability specialists rather than novice reviewers.
  •   The method can be applied at any stage of the design process, including early prototypes.
  •   HE is particularly valued for its speed and relatively low cost compared to lab-based testing.
  • Origins and Context
  •   The ten heuristics were empirically derived from analysis of real usability problems.
  •   Nielsen's 1994 refinement consolidated earlier, broader lists into ten actionable principles.
  •   The heuristics are intentionally high-level so they apply across diverse interface types.
  • When to Use Heuristic Evaluation
  •   Early-stage evaluation catches conceptual and navigation issues before development begins.
  •   Mid-fidelity evaluations surface interaction and feedback problems in interactive prototypes.
  •   Post-launch evaluations identify persistent issues and inform iterative improvement cycles.
  •   HE complements rather than replaces user testing — both methods surface different classes of issues.
  • Advantages and Limitations
  •   A major advantage is that HE does not require access to real end users.
  •   Evaluator expertise directly affects the quality and breadth of findings.
  •   HE can miss usability problems that only emerge during authentic user tasks.
  •   Using multiple evaluators significantly increases problem discovery rates.
  Notes: Heuristic Evaluation (HE) is a structured usability inspection method in which evaluators examine an interface against a set of recognized usability principles. This topic introduces the method's purpose, origins, and key advantages over other evaluation approaches.

TOPIC 2: Nielsen's Ten Usability Heuristics
  • Heuristic 1 — Visibility of System Status
  •   Users should never wonder whether their action was registered by the system.
  •   Feedback must be timely — delays greater than one second require a visible indicator.
  •   Status messages should be meaningful and located where the user's attention is focused.
  • Heuristic 2 — Match Between System and the Real World
  •   Interface language should reflect the vocabulary of the target user group, not developers.
  •   Icons and metaphors should map naturally to their real-world counterparts.
  •   Information should appear in a natural and logical order that reflects users' mental models.
  • Heuristic 3 — User Control and Freedom
  •   Undo and redo functions are essential implementations of this heuristic.
  •   Destructive actions should be reversible or require explicit confirmation before execution.
  •   Users should be able to cancel any multi-step process at any point without side effects.
  • Heuristic 4 — Consistency and Standards
  •   Internal consistency requires that identical actions produce identical outcomes throughout the interface.
  •   External consistency aligns the interface with platform-wide or industry-wide conventions.
  •   Inconsistent terminology forces users to expend cognitive effort resolving ambiguity.
  • Heuristic 5 — Error Prevention
  •   Constrain user input to valid options wherever possible to eliminate entry errors.
  •   Warn users before they commit to potentially destructive or irreversible actions.
  •   Design workflows that make errors difficult to make rather than easy to recover from.
  • Heuristic 6 — Recognition Over Recall
  •   Visible options reduce cognitive load by allowing users to recognize rather than recall choices.
  •   Instructions and relevant information should be visible or easily retrievable at the point of use.
  •   Minimizing the need to transfer information mentally between interface sections reduces errors.
  • Heuristic 7 — Flexibility and Efficiency of Use
  •   Novice and expert users have different interaction needs that the interface should accommodate.
  •   Keyboard shortcuts and hotkeys allow experts to bypass menu-driven navigation.
  •   Personalization features let users tailor frequently used functions for faster access.
  • Heuristic 8 — Aesthetic and Minimalist Design
  •   Each interface element should serve a clear purpose for the primary user task.
  •   Extraneous content reduces the signal-to-noise ratio and increases cognitive load.
  •   Visual hierarchy should direct user attention toward the most critical information first.
  • Heuristic 9 — Help Users Recognize, Diagnose, and Recover from Errors
  •   Error messages must use plain language that the target user can understand.
  •   Messages should clearly identify the specific problem rather than generic failure notices.
  •   Every error message should include a constructive path forward or suggested remedy.
  • Heuristic 10 — Help and Documentation
  •   Help documentation should be easy to find at the moment of need, not buried in menus.
  •   Content should be organized around user tasks rather than system features or components.
  •   Concise, step-by-step guidance is more effective than lengthy conceptual descriptions.
  Notes: This topic covers each of Nielsen's ten heuristics in detail, explaining their meaning, rationale, and common interface violations. Mastery of these principles is the foundation for conducting a valid heuristic evaluation.

TOPIC 3: The Heuristic Evaluation Process
  • Preparing for the Evaluation
  •   Evaluators should review any available personas or user profiles before starting.
  •   Define which interface sections or user flows are in scope for the current evaluation.
  •   Establish representative tasks or scenarios that guide the walkthrough of the interface.
  •   Agree on the version of the prototype to be evaluated so all evaluators review the same artifact.
  • Conducting the Individual Evaluation
  •   Evaluators must work independently to prevent anchoring bias from influencing findings.
  •   A minimum of two walkthroughs is recommended — one holistic, one heuristic-focused.
  •   Every identified problem should be documented with a reference to the heuristic it violates.
  •   Note the specific location of each violation so it can be reproduced and verified.
  • Documenting Usability Problems
  •   Each finding should reference the exact screen, component, or interaction step where it occurs.
  •   The problem description should explain what the violation is, not just that a violation exists.
  •   Naming the specific heuristic violated provides a principled basis for the finding.
  •   Including a recommended fix increases the actionability of the evaluation report.
  • Number of Evaluators
  •   A single evaluator finds only about one-third of all usability problems on average.
  •   Three to five evaluators is the recommended range for maximum cost-effectiveness.
  •   Each evaluator brings a unique perspective, collectively improving problem coverage.
  •   Adding more than five evaluators yields rapidly diminishing returns on new findings.
  Notes: Conducting a valid heuristic evaluation requires following a structured process that goes beyond simply reading the heuristics. This topic outlines the key phases of an HE, from preparation through individual evaluation to finding consolidation.

TOPIC 4: Severity Rating
  • Purpose of Severity Ratings
  •   Severity ratings transform qualitative findings into a prioritized action list.
  •   They help stakeholders make informed trade-off decisions about fix sequencing.
  •   Ratings provide a shared language for communicating problem urgency across teams.
  • Nielsen's Severity Rating Scale
  •   A rating of 0 means the evaluator flagged a potential issue but it does not constitute an actual problem.
  •   Ratings of 1 and 2 represent cosmetic and minor issues that should be addressed when resources allow.
  •   A rating of 3 indicates a significant problem that meaningfully impairs task completion.
  •   A rating of 4 represents a showstopper that prevents users from completing a primary task.
  • Factors Influencing Severity
  •   Frequency refers to how often users are expected to encounter the problem during normal use.
  •   Impact refers to how severely the problem disrupts the user's ability to complete their task.
  •   Persistence refers to whether the problem recurs or can be avoided after encountering it once.
  •   A violation that is both frequent and high-impact will almost always receive a high severity rating.
  • Assigning and Recording Ratings
  •   Severity ratings must be assigned before evaluators share or compare findings.
  •   Each rating should be justified with a brief rationale tied to frequency, impact, or persistence.
  •   Rating disagreements between evaluators are opportunities to refine problem descriptions.
  •   Final agreed ratings should be recorded alongside the problem description in the formal report.
  Notes: Severity ratings allow evaluators to prioritize usability problems by estimating the impact of each violation on the user experience. This topic explains the standard severity scale and how to apply it consistently.

TOPIC 5: Aggregating Findings Across Evaluators
  • Why Aggregation Is Necessary
  •   Individual evaluators each find only a subset of the total usability problems present.
  •   Aggregation maximizes problem coverage by combining the unique findings of each evaluator.
  •   The aggregated list is the primary deliverable that informs design revision decisions.
  • The Aggregation Meeting
  •   Each evaluator presents their complete findings list before group discussion begins.
  •   Duplicate issues are identified and merged into a single consolidated finding.
  •   Where evaluators disagree on severity, discussion should center on observable evidence.
  •   The output is a single master list with agreed problem descriptions and severity ratings.
  • Deduplication and Problem Merging
  •   Compare problem descriptions carefully — similar symptoms may reflect different root causes.
  •   Merge problems only when they share the same root cause and the same recommended fix.
  •   Keep related but distinct problems separate to avoid obscuring important nuances in the findings.
  •   Document which evaluators identified each problem to reflect breadth of discovery.
  • Negotiating Severity Across Evaluators
  •   Encourage evaluators to explain the reasoning behind their severity ratings before negotiating.
  •   Consensus should be grounded in observable evidence, not personal preference.
  •   Avoid simple mathematical averaging as it can produce ratings that no evaluator actually endorsed.
  •   When consensus is impossible, document the range of ratings and the rationale for each position.
  Notes: After individual evaluations are complete, findings must be systematically combined to create a single, deduplicated list of usability problems. This topic explains the aggregation process and how to resolve evaluator differences.

TOPIC 6: Writing Formal Heuristic Evaluation Reports
  • Report Structure and Components
  •   The executive summary provides a high-level overview for stakeholders who will not read the full report.
  •   The methodology section documents who conducted the evaluation, when, and under what conditions.
  •   Findings should be organized in a table sorted from highest to lowest severity.
  •   Each finding entry should include location, description, heuristic, severity, and recommended fix.
  •   A recommendations section may synthesize findings into broader design improvement themes.
  • Writing Effective Problem Descriptions
  •   Describe the problem objectively without subjective or emotionally loaded language.
  •   Specify the exact interface location — screen name, component, and interaction step.
  •   Link each description explicitly to the heuristic it violates to support the finding's validity.
  •   Avoid describing the desired solution in the problem description — keep problem and recommendation separate.
  • Formulating Recommendations
  •   Each recommendation should directly address the root cause identified in the problem description.
  •   Recommendations should be proportionate in scope to the severity of the problem.
  •   Where possible, reference established patterns or conventions that address the violation.
  •   Framing recommendations positively — what to do, not just what to avoid — is more useful to designers.
  • Using Visual Evidence
  •   Screenshots should be captured at the moment the violation is most visible or impactful.
  •   Annotations should clearly mark the specific element or area where the violation occurs.
  •   Captions below images should connect the visual evidence explicitly to the problem description.
  •   For interaction-based violations, short screen recordings may communicate the issue more effectively than static images.
  • Report Quality Standards
  •   Every finding must be anchored to a specific Nielsen heuristic, not general design intuition.
  •   Severity ratings must be accompanied by a brief justification referencing frequency, impact, or persistence.
  •   Language throughout the report should remain neutral, professional, and free of speculation.
  •   Recommendations must be feasible within the realistic constraints of the design project.
  Notes: The formal HE report is the primary deliverable that communicates findings to design teams and stakeholders. This topic outlines the structure, content requirements, and quality standards for professional HE reports.

TOPIC 7: Evaluating Peer Prototypes
  • Module Assignment Overview
  •   Students evaluate three distinct peer prototypes independently, without collaboration during the evaluation phase.
  •   A separate formal HE report must be produced for each prototype evaluated.
  •   All ten Nielsen heuristics must be systematically considered during each evaluation.
  •   Severity ratings must be applied to every documented finding using the standard 0–4 scale.
  • Maintaining Evaluator Independence
  •   Do not share or discuss findings with classmates until all individual evaluations are fully documented.
  •   Record findings as you discover them — do not rely on memory to reconstruct observations later.
  •   Independence ensures your report reflects your own expert assessment, not a group consensus.
  •   Collaboration before completion of individual reports undermines the validity of the evaluation.
  • Professional Conduct in Peer Evaluation
  •   All findings must be framed objectively with reference to heuristics and observable evidence.
  •   Avoid personal commentary about the prototype designer's skill, effort, or intent.
  •   Constructive recommendations respect the designer's creative direction while addressing genuine violations.
  •   Professional evaluators recognize that usability problems are a normal part of iterative design.
  • Calibrating Evaluations Across Prototypes
  •   Use the same systematic walkthrough process for each prototype regardless of perceived quality.
  •   Review all ten heuristics before beginning each new evaluation to reset your assessment frame.
  •   Do not let the quality of one prototype unconsciously shift the standard applied to others.
  •   A consistent number of walkthroughs per prototype helps control for evaluation depth variation.
  Notes: This module requires students to apply the full HE process independently to three peer prototypes. This topic outlines the expectations, workflow, and professional conduct standards for peer prototype evaluations.
