Introduction to Figma and the Prototyping Workflow

▶

Figma is a browser-based interface design and prototyping tool that has become a default environment for digital product teams. Unlike traditional desktop design applications, Figma stores the design file in the cloud, which means that the file you open is the same file your collaborators open at the same moment. This single architectural decision shapes almost everything about how the tool behaves: there is no "save" button in the conventional sense, version history is automatic, sharing is a matter of permissions rather than file transfer, and several people can edit the same screen simultaneously. Before you can design efficiently, you need a confident mental model of where things live in the interface, how a file is organised, how collaboration works, and how a static mockup becomes a clickable prototype. This topic builds that mental model and sets out the four-stage workflow that the rest of the module follows.

It is worth separating two ideas that beginners often conflate. Design mode is where you draw, arrange, and style objects. Prototype mode is where you wire those objects together into flows that simulate how the product behaves. Both modes act on the same file and the same layers — you switch between them using tabs at the top of the right-hand panel. A prototype in Figma is therefore not a separate export or a different document; it is a layer of behaviour described on top of the design you have already made. Understanding this saves a great deal of confusion later, particularly when a prototype link appears "broken" simply because a frame was renamed or deleted in design mode.

The Figma interface at a glance. The working environment is divided into four persistent regions: the left panel, the canvas, the right properties panel, and the toolbar across the top. Each has a distinct job, and learning to read them together is the first practical skill to acquire.

The left panel is your inventory of everything in the file. It has three tabs. The Layers tab shows the hierarchical tree of every frame, group, component instance, shape, and text object on the current page, with the topmost item in the list rendering in front of the items below it on the canvas. Nested items are indented, so a button containing a rectangle and a text label appears as a parent with two children, and you can expand or collapse branches to keep the list readable. The Pages section sits above the layer tree and lists the pages in the file. The Assets tab lists the components available to you — both the local components published in this file and any components from team libraries you have enabled. Dragging a component from the Assets tab onto the canvas creates an instance of it, which is the foundation of consistent interface work.

The canvas is the infinite workspace. There are no page boundaries or print margins; you can zoom out and place an entire mobile app's worth of screens side by side, or zoom in to nudge a single pixel. Objects placed directly on the canvas rather than inside a frame still exist, but they are not part of any screen and cannot be prototyped from in the usual way, so most serious work happens inside frames. A frame is the fundamental container in Figma: it defines a screen, a card, a section, or any bounded region, and it can clip its contents, carry a layout grid, hold auto-layout settings, and act as a destination in a prototype. Each page has its own infinite canvas, so moving between pages is like moving between separate workspaces that happen to share the same file, libraries, and styles.

The right properties panel is contextual: its contents change entirely depending on what you have selected. With nothing selected, it shows page-level properties such as background colour, and the local styles and variables defined in the file. Select a rectangle and you see alignment controls, X/Y position, width and height, constraints, corner radius, fill, stroke, effects, and export settings. Select a text layer and a typography section appears with font family, weight, size, line height, letter spacing, and alignment. Select a frame and you gain layout grid and clipping options. Select an instance of a component and you see the instance swap control plus any component properties the author exposed, such as boolean toggles for an icon or text properties for a label. Selecting two or more objects adds distribute and tidy-up controls and lets you apply the same property to all of them at once. Learning to expect this contextual change prevents the common beginner frustration of "the option I need has disappeared" — usually it simply means the wrong object, or the wrong level of the hierarchy, is selected.

The toolbar at the top provides the creation tools and the global controls. From left to right it typically offers the move and scale tools, the frame tool (keyboard F), the shape tools (rectangle R, ellipse O, line, arrow, polygon, star), the pen and pencil for vector drawing (P), the text tool (T), the comment tool (C), and the hand tool for panning. Alongside these sit the component actions — create component, detach instance — and on the right of the toolbar you find the share button, the present (play) button that launches the prototype, and the zoom controls. Pages and file organisation. A Figma file is not a single document surface but a collection of pages, each with its own infinite canvas. Pages behave like tabs: switching pages changes what the layer panel and the canvas show, while styles, components, and the file's version history remain shared across the whole file. This makes pages the natural unit for separating stages of work or sections of a product. A typical student project file might be organised like this:

  • 📕 Cover — a single frame named with the project title, used as the file thumbnail so the file is recognisable in the project dashboard.
  • 🔍 Research & references — competitor screenshots, mood boards, personas, and user journey notes that inform the design but are not part of it.
  • ✏️ Wireframes — low-fidelity, greyscale layout explorations.
  • 🧩 Components — the master components and styles: buttons, inputs, cards, navigation bars, icons.
  • 🎨 UI — High fidelity — the finished screens built from those components.
  • ▶️ Prototype — either the flow-ready copies of screens or, more commonly, the same high-fidelity page with prototype connections applied.
  • 🗑 Archive — superseded explorations kept for reference rather than deleted, so that decisions can be justified later.

Numbering or prefixing page names with emoji is a widespread convention because it imposes a visual order and makes the page list scannable at a glance. Whatever convention you choose, apply it consistently; a reviewer who opens your file should be able to find the current work in under ten seconds.

Frame naming deserves more attention than it usually gets. Figma names new frames Frame 1, Frame 2, and so on, and leaving those defaults in place causes real problems. In prototype mode, every connection's destination is identified in the interface by the frame's name, so a flow built from Frame 17 → Frame 23 → Frame 8 is almost impossible to audit or repair. The presentation view and any shared prototype link also display frame names, and developers inspecting the file use them to map screens to routes in code. A readable scheme uses a numeric prefix for flow order plus a descriptive name, for example:

01 Splash
02 Onboarding - Step 1
03 Onboarding - Step 2
04 Sign in
05 Home - Default
05a Home - Empty state
05b Home - Loading
06 Search - Results

Notice two things about that scheme. First, numbering reflects the user's path rather than the order in which you happened to draw the screens, so a collaborator can read the file like a storyboard. Second, state variants of the same screen share a number with a letter suffix, which keeps Home - Empty state adjacent to Home - Default in the layer list instead of stranded at the bottom. Keep names short enough to read in the narrow left panel, and avoid spaces-only differences such as Home and Home , which look identical but are distinct strings.

Grouping and sections. Once a page holds twenty or thirty frames, spatial organisation matters as much as naming. Figma's section tool (keyboard ⇧S) creates a labelled, coloured region on the canvas that you can drag frames into; the section's name floats above it at any zoom level, so when you zoom out to see the whole page you read Onboarding, Core shopping flow, and Account settings rather than a wall of unlabelled rectangles. Sections can be collapsed to hide their contents, and can be marked as "ready for development", which signals status to the rest of the team. Where sections are not available or not wanted, a simpler alternative is a large text label placed above each cluster of frames, or an oversized background frame acting as a container. The goal in every case is the same: a person who has never seen the file should be able to understand its structure from a zoomed-out view, without clicking anything. Arranging flows left-to-right in the order the user experiences them, with alternative branches stacked vertically beneath the main path, reinforces that readability.

Collaboration and sharing basics. Because the file lives in the cloud, sharing is handled through permissions on a link rather than by sending a copy. The share dialog lets you set access at two levels — who can open the file at all, and what they can do once inside. The three practical access levels are:

Two further choices in the share dialog matter. You can restrict access to only people invited to this file or open it to anyone with the link; the latter is convenient for coursework submission but means the link is effectively public, so it should never carry confidential client material. You can also share a prototype link rather than a file link, which opens the recipient straight into presentation mode at a chosen starting frame — much better for user testing, because the participant sees only the product, not the scaffolding around it.

Multiplayer editing is the most visible consequence of the cloud model. When collaborators are in the file, their cursors appear on the canvas in colour, each labelled with a name, and you can see their selections highlight in real time. Clicking a collaborator's avatar in the toolbar activates observation mode, which follows their viewport as they move, pan, and zoom — invaluable for a walkthrough or a remote critique, since one person can drive while everyone else watches the same screen. Simultaneous editing is genuinely concurrent: two people can style different components on the same page without conflict. Conflicts that do arise are mechanical rather than technical — two designers restyling the same button will simply overwrite each other — so a short verbal agreement about who owns which area of the canvas is still good practice. Figma also supports a branching workflow on paid plans, where a copy of the file is edited independently and later merged back, which is the equivalent of a feature branch in software version control.

Comments are created with the comment tool (C) and can be pinned to a specific point on the canvas, attached to a particular object so the pin follows the object if it moves, or placed on a screen inside the prototype viewer. Each comment supports threaded replies, @-mentions that send a notification to a named collaborator, emoji reactions, and a resolve action that hides the thread once addressed. The discipline worth adopting is to make feedback specific and actionable: "the tap target on this icon is 24px, below the 44px minimum for touch" is useful; "this looks off" is not. Pinned, contextual feedback is also far more traceable than feedback in a separate chat thread or email, because the comment sits permanently next to the thing it describes.

Version history runs automatically. Figma continuously checkpoints the file, and the history panel lists each checkpoint with a timestamp and the collaborators who contributed to it. You can open any past state to inspect it, restore it to become the current state, or duplicate it into a new file to explore an old direction without disturbing the live work. Crucially, you can also name a version manually — for example "v1.0 submitted for formative feedback" or "post-usability-test revisions" — which creates a meaningful milestone in a long list of automatic saves. Naming versions at the end of each significant work session turns an opaque timeline into a documented design history, which is exactly what you need when a tutor or client asks why a decision changed. Note that on free plans the browsable history window is limited in duration, so naming versions and duplicating key milestones into separate files is a sensible precaution.

From mockup to prototype: the module workflow. The remainder of the module follows a deliberate four-stage sequence. The order is not arbitrary: each stage removes work from the stage that follows it. Designers who skip ahead — building fifteen detailed screens before defining a single component — typically spend longer fixing inconsistencies than they saved by starting quickly.

Stage one — frame setup and layout grids. You begin by choosing a target device and creating frames at the correct dimensions. Figma's frame presets include common sizes such as 390 × 844 for a modern iPhone, 360 × 800 for a typical Android handset, 1440 × 1024 for a desktop breakpoint, and 1024 × 768 for a tablet. Designing at the real pixel dimensions matters because touch target sizes, type legibility, and the amount of content visible "above the fold" are all meaningless in the abstract. Onto each frame you add a layout grid. For mobile, a common configuration is a 4-column grid with a 16px margin and a 16px gutter; for desktop, 12 columns with 24px gutters and a maximum content width. A second, separate grid set to a uniform 8px row-and-column pattern enforces the 8-point spacing system that keeps vertical rhythm consistent — every margin, padding value, and gap becomes a multiple of 8 (with 4 permitted for fine adjustments). Grids are visual guides only: they do not constrain objects, but they make misalignment immediately obvious, and they give you a principled answer to "how much space should go here?"

Stage two — components before detail. Before styling individual screens, you identify the elements that will recur and build them once as components. A component is a master object; every copy you place is an instance that inherits from the master, so editing the master updates every instance in the file. The typical first set includes a button, a text input, a navigation bar, a list item or card, an avatar, and an icon set. Variants group related states of the same component into a single switchable set — a button with variants for primary/secondary style, default/hover/pressed/disabled state, and small/medium/large size. Building these early produces two benefits. First, consistency becomes the default rather than something you have to police: all your buttons share corner radius, padding, and type because they are literally the same object. Second, late changes become cheap — if the client changes the brand colour the week before submission, you edit one component and one colour style rather than hunting through forty screens. Paired with styles (named, reusable definitions of colour, type, effects, and grids) and variables (named tokens for values such as spacing or colour that can be switched wholesale for a dark theme), components turn an ad-hoc file into a small design system.

Stage three — auto-layout for responsiveness. Auto-layout converts a frame into a flexible container whose children are arranged along a horizontal or vertical axis with defined spacing and padding, conceptually similar to CSS Flexbox. Applying it (⇧A) lets you specify direction, the gap between items, padding on each side, alignment of the children within the container, and whether the frame hugs its contents, fills the available space, or stays at a fixed size. The practical consequence is that content changes no longer break layouts: lengthen a button's label and the button grows around the text while its padding stays constant; delete a row from a list and the rows below move up and the container shrinks to fit; add a third item to a navigation bar and the items redistribute automatically. Auto-layout frames nest, so a card might be a vertical auto-layout frame containing an image, a vertical text stack, and a horizontal row of two buttons — each level responding independently. This is also the stage at which the design starts to behave like real software, which makes handover to developers much more faithful.

Stage four — connecting screens into a prototype. With the screens built, you switch to the Prototype tab and drag connection nodes from an object on one frame to the frame it should lead to. Each connection is defined by a trigger (what the user does: on click/tap, on drag, while hovering, while pressing, after delay, on key press, mouse enter/leave), an action (navigate to, open overlay, swap overlay, close overlay, back, scroll to, change to a variant, open link), and an animation (instant, dissolve, move in/out, push, slide in/out, or smart animate, each with a direction, easing curve, and duration). Smart animate deserves special mention: it compares layers with matching names across the two frames and tweens their differences in position, size, opacity, and rotation, which is how designers produce convincing transitions such as a card expanding into a detail view — and it is also the clearest payoff for having named layers consistently in stages one and two. You also set a starting frame for each flow, so a single file can present several named flows (onboarding, purchase, account settings) from one prototype link. Pressing present runs the prototype in the browser, where it can be tested on a real device via the Figma mobile app or sent to participants as a link that records nothing but allows them to click through as if the product existed.

A worked illustration of how the stages compound: imagine a simple recipe app. In stage one you create nine frames at 390 × 844, named 01 Splash through 09 Saved recipes, each with a 4-column grid and 16px margins. In stage two you build a Recipe card component — image, title, cooking time, save icon — plus a Button with four variants and a Tab bar with an active-state variant for each tab. In stage three you make the recipe card an auto-layout frame so that a long recipe title wraps and pushes the metadata down rather than overflowing, and you make the home screen's list an auto-layout stack with a 12px gap so cards can be added or removed freely. In stage four you connect the card to 07 Recipe detail with an on-tap navigate and a smart animate transition that expands the card image into the detail header, wire the tab bar to switch between top-level screens, and add an overlay for the "saved to collection" confirmation toast that closes after 1,500ms. Each stage took the previous stage's output as raw material; none of the work had to be redone.

Two habits will serve you throughout. First, name as you go: layers, frames, components, styles, and saved versions. Almost every advanced Figma feature — smart animate, component swapping, developer handoff, prototype auditing — depends on names being meaningful. Second, test early and often: press present after wiring even two screens together, because a prototype that is only ever viewed in design mode tends to accumulate broken links, missing states, and dead ends that are tedious to unpick the night before a deadline.

Frames, Grids, and Screen Layout

▶

Every screen you design in Figma begins life as a frame. Before a single button, icon, or paragraph of body copy is placed, the frame establishes the canvas on which the interface lives: its width and height, its clipping behaviour, its grid, and its role in the prototype. Understanding frames — and the layout systems that sit inside them — is the difference between a file that scales gracefully from a 320 px phone to a 1440 px desktop and a file that collapses the moment someone resizes it. This topic walks through the frame as a structural container, the layout grids that bring order to its contents, the constraint system that makes those contents responsive, the device presets and safe areas that ground the design in real hardware, and finally the flows that turn a scattered collection of screens into a coherent, navigable user journey.

What Is a Frame?

A frame in Figma is a container node that behaves like a viewport. Conceptually it is closest to a <div> in HTML or a UIView in iOS: it has its own coordinate space, its own fill, stroke, corner radius, and effects, and anything placed inside it is positioned relative to its top-left corner rather than to the canvas. This relative positioning is what makes frames so powerful — move the frame and everything inside travels with it, preserving internal offsets exactly.

When you press F (or A in newer builds) and draw a frame, the properties panel offers a list of device presets. Selecting one gives the frame fixed dimensions that match real hardware: an iPhone 14 preset produces a 390 × 844 frame, an iPhone 14 Pro Max produces 430 × 932, an Android "Pixel 7" produces 412 × 915, an iPad Pro 11" produces 834 × 1194, and a Desktop preset produces 1440 × 1024. These numbers are expressed in points or logical pixels, not physical device pixels — a distinction that matters enormously when you reach the export stage, and which is discussed later in this topic. Designing inside a correctly sized frame means that a 44 px tall button really is a 44 pt tap target on the device, not an abstraction you have to mentally rescale.

Frames clip their contents by default when the "Clip content" checkbox is ticked in the properties panel. Anything that extends past the frame boundary is simply not drawn. This mirrors the behaviour of a real screen: a horizontally scrolling carousel of product cards may contain twelve cards, but the device only ever renders the three that fall within the visible viewport. Clipping lets you build that illusion honestly — you lay out all twelve cards in a row that is 2,000 px wide, drop it inside a 390 px frame, and the frame hides the overflow exactly as the device would. If you untick "Clip content", the overflow becomes visible on the canvas, which is useful during construction (you can see and drag the off-screen cards) but misleading in a presentation. A common workflow is to untick clipping while building, then re-tick it before the prototype review.

Nested frames are the real structural workhorse of a Figma file. A screen frame contains a header frame, a content frame, and a tab bar frame; the header frame in turn contains a back-button frame and a title. Each level of nesting creates an independent coordinate space and an independent set of layout rules. This matters because both of Figma's two most important features — components and auto-layout — require frames. A component must be a frame (or a shape promoted to one) to accept auto-layout, padding, and resizing behaviour; an auto-layout stack is a frame with a direction, a gap, and a padding value attached. Building a card as a nested frame rather than a group means you can later give it padding: 16, a vertical gap of 8, and "Hug contents" sizing so it grows automatically when the description text gets longer.

The distinction between frames and groups is frequently misunderstood, and it has direct consequences for prototyping. A group is merely a selection convenience: its bounding box is computed from the union of its children, it has no independent fill or clipping, and it cannot hold auto-layout or layout grids. Critically, frames appear as distinct nodes in the prototype flow whereas groups do not — you can set a frame as a flow starting point, scroll within it, apply "Fix position when scrolling", or navigate to it with an interaction, but none of these are available to a group. Groups also resize their children proportionally when you drag their edges, which is rarely what you want for interface layout.

Applying Layout Grids

A layout grid is a non-printing scaffold attached to a frame that gives you repeatable alignment decisions. Instead of eyeballing where a card should start, you snap it to a column. Figma offers three grid types — Grid (a uniform square mesh, usually 8 px, for baseline spacing), Columns, and Rows — and you add them from the Layout Grid section of the properties panel with the + button.

Column grids define the horizontal divisions against which text blocks, images, and interactive elements are aligned. The industry convention for desktop web is a 12-column grid, because 12 divides evenly by 2, 3, 4, and 6, allowing halves, thirds, quarters, and sixths without fractional columns. Mobile layouts typically use 4 columns (iOS/Material convention) or 6; tablets commonly use 8. A product grid that spans three columns on desktop can collapse to spanning two of four columns on mobile, and because both layouts are expressed in the same column language, the translation is systematic rather than improvised.

Gutter and margin settings control the breathing room. The gutter is the gap between adjacent columns; the margin is the inset from the frame edge to the first and last column. Figma offers three column behaviours that interact with these values:

  • Stretch — you specify the count, gutter, and margin, and Figma computes the column width so the grid always fills the frame. This is the correct choice for responsive web frames, because the grid adapts when you resize the frame.
  • Center — you specify the count, gutter, and a fixed column width; the resulting block is centred in the frame. Useful for a fixed-width content well inside a full-bleed page.
  • Left / Right — the grid is anchored to one edge with a fixed column width, leaving the remaining space free. Useful for asymmetric layouts such as a documentation page with a sidebar.

If those fractional values produce blurry half-pixel edges, adjust the margin to 84 px so the columns resolve to a whole number.

Multiple grids can be stacked on a single frame. A professional desktop frame often carries three simultaneously: an 8 px square grid to enforce consistent vertical rhythm and spacing increments, a 12-column stretch grid for horizontal composition, and sometimes a row grid to mark a fixed header band and footer band. Each grid has its own colour and opacity swatch, so you can make the 8 px mesh a faint 3% red while the columns are a 10% blue — otherwise the overlays become visual noise. Toggle all grids on and off with Ctrl/Cmd + Shift + 4 (or Ctrl/Cmd + G in some versions) while you work, and save grid definitions as grid styles so every mobile frame in the project inherits identical settings with one click. Shared grid styles are the single most effective guard against drift across a large file.

Grids are visible only in the editor. They are an authoring aid, not content: they do not appear in exported PNG, JPG, SVG, or PDF assets, and they do not render in Presentation mode or in a shared prototype link by default. Developers inspecting the file in Dev Mode can read the grid definition as a specification, which is exactly the right place for it. If you deliberately want a visible grid in a presentation — to explain your layout logic in a design critique, for instance — you must draw it as real geometry (rectangles or lines) on a separate layer, because the layout grid itself will never be exported.

Constraints and Responsive Anchoring

A grid tells you where to place something once; constraints tell Figma what should happen to that element when its parent frame changes size. Every direct child of a frame carries a pair of constraints — one horizontal, one vertical — set in the Constraints widget at the top right of the properties panel. Constraints are evaluated relative to the immediate parent frame, which is why nesting matters: a button constrained "Right" inside a card frame pins to the card's right edge, not the screen's.

Horizontal constraints offer five options:

  • Left — the distance from the element's left edge to the parent's left edge is preserved; the element keeps its width and drifts away from the right edge as the frame widens. The default, and correct for most left-aligned content such as back arrows and headings.
  • Right — the distance to the parent's right edge is preserved. Correct for trailing icons, "Done" buttons, and close affordances.
  • Left and Right — both distances are preserved, so the element's width stretches to absorb the change. This is the responsive workhorse: a search field with 16 px of inset on each side will remain 16 px from both edges on a 320 px frame and a 430 px frame, growing from 288 px to 398 px automatically.
  • Center — the element's centre stays at the same proportional midpoint; the offset from the parent's centre is preserved and the width is unchanged. Correct for a centred navigation-bar title or a modal dialog.
  • Scale — the element's position and size change proportionally with the frame, as a percentage. Appropriate for full-bleed hero imagery and decorative background art, but dangerous for text and controls, because it produces non-standard font sizes and tap targets.

Vertical constraints mirror these exactly: Top, Bottom, Top and Bottom (stretch), Center, and Scale. Top pins an element a fixed distance below the frame's top edge; Bottom pins it above the bottom edge; Top and Bottom stretches its height; Center holds it at the vertical midpoint; Scale resizes proportionally. A scrollable content area between a fixed header and a fixed tab bar is the classic "Top and Bottom" case — as the frame grows from an iPhone SE's 667 px height to an iPhone 14 Pro Max's 932 px, the content region absorbs all 265 px of the difference while the chrome stays put.

Combining constraints with fixed dimensions is how you pin chrome reliably. Consider a navigation bar built as a nested frame 390 × 56 placed at y = 0 inside the screen frame. Give the bar a vertical constraint of Top and a horizontal constraint of Left and Right, and leave its height fixed at 56. Now, whichever device preset you resize the parent to, the bar remains exactly 56 px tall, flush to the top, and spanning the full width. Its children — the back arrow, the title, the overflow menu — carry their own constraints relative to the bar, so the whole assembly behaves as a single responsive unit. To test it, select the parent frame and drag a side handle while watching the result; if something behaves unexpectedly, the fault is almost always a constraint set on the wrong nesting level.

Finally, an important precedence rule: constraints are superseded by auto-layout when both are applied to the same element. Once a parent frame has auto-layout turned on, its children are positioned by the auto-layout algorithm — direction, gap, padding, alignment, and distribution — and their individual X/Y constraints are ignored. What remains available is the resizing behaviour of each child: "Fixed width/height", "Hug contents", and "Fill container". "Fill container" is the auto-layout analogue of a Left-and-Right stretch; "Hug contents" shrinks the frame to its children. Constraints do not disappear entirely, though — a child that is marked as absolute position inside an auto-layout frame (the little pin icon in the properties panel) steps outside the flow and once again honours its constraints, which is exactly how you overlay a notification badge on the corner of an auto-layout icon button. Understanding this hierarchy prevents the common frustration of setting a constraint and seeing nothing happen.

Safe areas are the regions of the screen that the operating system reserves for its own chrome, or that hardware intrudes upon. On modern iPhones these include the 44–59 px status bar and notch/Dynamic Island at the top, the 34 px home-indicator band at the bottom, and small corner radii that clip rectangular content. A useful technique is to place a semi-transparent "safe area" rectangle or an outlined guide layer on a locked layer at the top of your frame stack while composing, then hide it for presentation — or to build it into a reusable screen template component so every new screen starts correctly.

The caveat is that mockups are presentation assets — never design inside them, and never let a glossy render disguise a layout that has not been tested at real size on a real device.

Designing at 1× and exporting at 2× or 3× is the rule that keeps assets crisp on high-density displays. Because a phone's physical pixel density is two or three times its logical point grid, a 24 × 24 icon drawn at 1× must be delivered as a 48 × 48 bitmap for a 2× screen and 72 × 72 for a 3× screen, or it will appear soft. Second, keep your source artwork on whole-pixel coordinates at 1×. A related habit is to name layers for export before you export them. Figma builds the filename from the layer name, so a layer called Frame 427 becomes Frame 427@2x.png, which tells a developer nothing. Adopting a slug convention such as ic-search, img-hero-onboarding, or illus-empty-cart turns the export panel into a usable asset-delivery pipeline. Slashes in layer names create folders inside the exported ZIP, so naming a layer icons/search produces icons/search@2x.png — a small trick that saves considerable tidying.

Organising Screens with Flows

Once you have a dozen correctly built frames on the canvas, the remaining problem is narrative: which screen comes first, what leads to what, and how does a reviewer experience the design without you standing beside them explaining it. Figma's answer is the flow.

A flow represents one complete user journey — a self-contained task with a beginning and an end. Typical flows in a consumer app include Onboarding (splash → value propositions → permissions → account creation), Authentication (login → forgotten password → reset → success), Browse and Search, Checkout (cart → delivery → payment → confirmation), and Settings. Separating journeys this way does real cognitive work. It makes the file legible to collaborators, it allows you to share a link that opens on exactly the journey a stakeholder needs to review rather than dumping them at screen one of ninety, and it forces you to think in terms of tasks and goals rather than isolated pretty screens. A flow is also the natural unit for usability testing: you give a participant a task ("buy the blue jacket in size M"), and the flow is the path you expect them to take.

In Figma, a flow is created in the Prototype tab of the right-hand panel. Select the frame that should begin the journey and click the + next to "Flow starting point". Figma attaches a labelled badge to the top-left of that frame on the canvas and adds an entry to the Flows list, which you can rename (Checkout, Onboarding — new user) and annotate with a description. Starting frames become entry points during preview: when you press Present, the prototype opens on the selected flow, and the flow list appears in the viewer's sidebar so the audience can jump between journeys without you re-sharing links. You can also copy a direct link to an individual flow. A frame can only be the starting point of one flow, but a single file can contain as many flows as the product has journeys.

Good flows depend on disciplined naming. Sequential names such as Login-01 Empty, Login-02 Typing, Login-03 Error, Login-04 Success encode both the journey and the order, which keeps the layers panel sorted sensibly and makes the canvas self-documenting. Because Figma's layer list sorts frames by their stacking order rather than alphabetically, the numeric prefix is what gives you reliable, scannable order. Combine the naming with physical arrangement: lay each flow out as a left-to-right row on the canvas, one row per journey, with branches stacked vertically beneath the screen they branch from. The spatial map then mirrors the logical map, and anyone opening the file can read the product's structure at a glance. A Figma section (Shift + S) drawn around each row reinforces this, since sections can be named, collapsed, and marked "Ready for development".

A common scheme assigns a hue per state of completion or per journey: blue for onboarding, green for the happy-path checkout, amber for error and edge-case screens, grey for screens that are parked or deprecated. During a design review, the reviewer can see at once that the three amber frames are the error states and that the grey cluster is out of scope for this sprint. Keep the saturation low — a 5–10% tint is enough to read as a grouping without competing with the interface colours inside the frame. If you tint the screen frames themselves rather than the sections, remember to reset them to the intended background colour before the prototype is presented, or build the tint into a locked backing rectangle behind each row instead.

Finally, flows and the structural concepts above reinforce one another. A flow is only trustworthy if its frames are genuine frames rather than groups, because groups cannot be flow starting points or navigation destinations. The journey only looks credible on a phone if each frame uses an accurate device preset and respects safe areas. And the whole set only survives a change of device size if constraints — or, where appropriate, auto-layout — have been set deliberately on every child. Frames, grids, constraints, presets, and flows are not five separate techniques; they are one layered system for making a design file that behaves like a product.

Building a Component Library

Building a Component Library

▶

A component library is the structural backbone of any serious interface project. Rather than drawing a button thirty-four times across twelve screens and hoping each copy stays visually identical, you build one authoritative version of that button and place controlled copies of it wherever it is needed. When the brand colour changes, when the corner radius is softened, when the label font moves from 14px to 15px, you make that change once and every screen in the file inherits it. In Figma this system is built from components, variants, styles, and ultimately a published team library. Learning to build and maintain such a library is the difference between a prototype that looks hand-assembled and one that behaves like a real product. The sections below work from the smallest unit — a single component — up to a shared, versioned library used across multiple files.

What Is a Component?

A component in Figma is a reusable design element whose definition lives in one place and whose appearance is propagated to every copy. The vocabulary matters here because Figma's interface uses it consistently, and so do design teams in handover conversations.

The main component (sometimes called the master or source component) is the single source of truth. It is the original object you created and converted; it carries a solid purple four-diamond icon in the layers panel. Everything else derives from it. Best practice is to keep main components out of the working screens where they could be accidentally moved, resized, or deleted. Two common conventions are:

  • A dedicated page in the file, often named 🧩 Components or Library, where all main components are laid out in a tidy grid with labels.
  • A separate Figma file entirely — a design system file — which is then published as a team library and consumed by product files.

The second approach scales better. If main components sit in the same file as your screens, every designer editing a screen has the power to break the system. Separating them creates a deliberate boundary between "using the system" and "changing the system."

An instance is a live copy of a main component placed on the canvas. It carries a hollow (outline) diamond icon. An instance inherits all properties of its main component — geometry, fills, strokes, effects, text content, auto layout settings, nested children — but allows you to apply local overrides on top of that inheritance. Overrides are the controlled exceptions to the rule. Typical overrides include:

  • Text content: a Button instance that says "Continue" instead of the default "Label".
  • Swapping a nested instance: replacing the default chevron icon with a download icon.
  • Changing a fill, stroke, or effect on a specific layer.
  • Toggling a layer's visibility, if the component exposes that as a boolean property.
  • Resizing the instance, if the component's constraints and auto layout allow it.

What you cannot do on an instance is restructure it: you cannot add new layers, delete existing layers, or reorder children. Figma deliberately prevents this because the structure is what makes the inheritance relationship predictable. If you need structural freedom, you need either a different component or a detached copy.

The crucial behaviour is propagation. Editing the main component updates every instance across the file simultaneously, and across every file that consumes the library once the update is published and accepted. Suppose you have a Card component used 60 times. You open the main component, change the shadow from 0 1px 2px rgba(0,0,0,0.1) to 0 2px 8px rgba(0,0,0,0.08), and all 60 instances soften immediately. Importantly, propagation respects overrides: if an instance had its own text content, that text survives the update. Figma attempts to reconcile the incoming change with the local override, and the local override generally wins for the specific property it touched.

Detaching an instance (right-click → Detach Instance, or Ctrl/Cmd + Alt + B) converts it into an ordinary frame or group. The purple diamond disappears, the link to the main component is severed, and future edits to the main component no longer reach it. Detaching is occasionally legitimate — for example, when producing a one-off marketing illustration based on a component — but in product work it is usually a warning sign. A detached card is a card that will silently drift out of sync with the rest of the product. A useful team rule: if you feel the need to detach, the component is probably missing a property you should add instead.

Creating Components from Existing Elements

Most components are not designed in the abstract; they emerge from the work. You draw a button on a sign-up screen, then draw a similar one on a settings screen, and at the third repetition you recognise a pattern worth formalising. The conversion itself is trivial: select the element — ideally an auto layout frame containing a text layer and whatever icons or backgrounds it needs — and press Ctrl/Cmd + Alt + K (or use the "Create component" button in the toolbar, which looks like four diamonds). The selection becomes a main component in place, and any identical copies you make afterwards are instances.

A practical workflow for extracting a component from existing work:

  • Choose the best existing copy of the element — the one with correct spacing, colour styles already applied, and sensible layer names.
  • Wrap it in an auto layout frame (Shift + A) so it can grow and shrink with its content.
  • Rename the internal layers meaningfully: Label, Icon Leading, Icon Trailing, Background. These names are what Figma uses to match overrides later, so they are functional, not cosmetic.
  • Press Ctrl/Cmd + Alt + K.
  • Move the main component onto the components page and replace the original on-screen element with an instance.

Naming with slash notation is how you impose order on a growing library. Figma reads the forward slash as a folder separator in the assets panel. A component named Button/Primary/Large appears nested under Button → Primary → Large. A consistent naming scheme typically runs from general to specific:

Second, naming must be stable. Renaming Button/Primary to Buttons/Primary later will scatter your assets panel and confuse teammates searching for it.

Components should be self-contained — they must not depend on the sizing, padding, or position of whatever frame they happen to sit inside. A button whose width is set to "Fill container" is fine, because fill is a relationship the component declares about itself. A button that only looks right because the screen frame happens to be 375px wide is not self-contained; drop it into a 768px tablet layout and it breaks. Practical tests for self-containment:

  • Place an instance on a blank canvas area with no parent frame. Does it still render correctly?
  • Change the text label to something twice as long. Does the component grow gracefully (auto layout, hug contents) or does the text overflow the background?
  • Resize the instance to the extremes of its intended range. Do internal paddings hold, or do elements collide?

Finally, every main component has a description field and can be given a thumbnail. Component Variants

Early Figma libraries suffered from combinatorial explosion: a button with three types, three sizes, and five states required 45 separate components cluttering the assets panel. Variants solve this by collapsing related components into a single component set — a dashed purple container — within which each member is distinguished by named properties.

To create a set, select two or more related main components and click "Combine as variants" (or press Ctrl/Cmd + Alt + K on a multi-selection in recent versions). Figma infers properties from the existing names if they use slash notation, or creates a generic Property 1 that you then rename. Each property holds multiple values, entered in the right panel separated by commas:

Property name Values Control type in instance panel
Type Primary, Secondary, Ghost, Destructive Dropdown
Size Small, Medium, Large Dropdown
State Default, Hover, Pressed, Focused, Disabled Dropdown
Icon True, False Boolean toggle

With those four properties the set contains 4 × 3 × 5 × 2 = 120 permutations, yet the assets panel shows a single entry named Button. A designer drops one instance and configures it through dropdowns in the right panel, which is far faster than hunting through a list of 120 names.

In practice you rarely need every permutation. A healthy approach is to build the realistic combinations and accept that the matrix is sparse — for instance, a Destructive button may only need Default, Hover, and Disabled states. Figma handles missing combinations by falling back to the nearest match, though explicit coverage of the states your prototype actually uses is safer.

A significant convenience is that switching variants preserves overrides where layer names match. If an instance of Button has its Label text overridden to "Save changes" and its Icon Leading swapped to a checkmark, changing State from Default to Hover keeps both of those overrides — provided the Hover variant also contains layers named Label and Icon Leading in equivalent structural positions. This is precisely why layer naming is functional rather than decorative. If the hover variant's text layer is called Label copy or Text 12, the override will be dropped and the button will revert to "Label" mid-prototype — a confusing and very common bug.

The same discipline applies to property and value naming consistency. Figma matches variants for prototype interactions and for the "Change to" smart animate behaviour by property name and value. Consider a set where one component is named State=Hover and another state=hovered: these are treated as distinct values of distinct properties, and interactive components will not resolve cleanly between them. Establish a convention and hold to it:

  • Property names in Title Case and singular: State, Size, Type, not states or sizes.
  • Boolean properties phrased positively: Has Icon with True/False, not No Icon.
  • The same value vocabulary across every component in the library: if buttons use Default, Hover, Pressed, Disabled, then inputs, list rows, and cards should use the same four words rather than Rest, Hovered, Active, Inactive.
  • Order values logically in the property list — Small, Medium, Large, not alphabetically as Large, Medium, Small — because that order is what appears in the dropdown.

Consistent variant naming pays off directly in prototyping. Figma's interactive components feature lets you wire "While hovering → Change to → State=Hover" inside the component set itself. Every instance anywhere in the file then responds to hover without any per-screen prototyping work. If the naming is inconsistent, you are forced to rebuild those interactions instance by instance.

Slots, Nesting, and Component Composition

Real interfaces are composed, not monolithic. A Card contains an Avatar, a Badge, a Button, and an Icon. When you place an instance of one component inside the definition of another, you create a nested component. The nested object remains a true instance: it keeps its own link to its own main component, it can receive its own overrides, and it updates when its source changes. This is the mechanism that makes a design system compound in value — fix the icon grid once and every icon inside every card, list row, toolbar, and empty state corrects itself.

Figma exposes nesting in two important ways:

  • Nested instance overrides bubble up. Select a Card instance on the canvas and you can drill into its nested Button to change the label or swap its variant, without detaching anything. Deep-select with Ctrl/Cmd + click or expand the layer in the layers panel.
  • Exposed nested properties. In the component set's properties panel you can mark nested instances as exposed, which lifts their controls into the parent instance's right-hand panel. A designer selecting a Card then sees Button → Type and Button → Label directly, with no drilling required. This is Figma's closest equivalent to a "slot" or "prop pass-through" in code.

The slot pattern itself is usually implemented with an instance swap property. You place a small placeholder component (for example Slot/Empty, a transparent 24×24 frame) inside the parent, then define an instance swap property pointing at it. On any instance of the parent, the designer picks what fills the slot from a dropdown of eligible components. A List Row might expose a Trailing Slot that can be filled with a chevron, a toggle, a checkbox, a badge, or nothing — one component covering five real interface patterns.

Composition is the design-system principle underlying all of this: keep individual components small, focused, and single-purpose, then assemble them. The alternative — a single enormous Product Card component with forty internal layers and nine boolean toggles — is brittle. Small components are easier to reason about, easier to test against edge cases, easier to document, and far easier to change. A good heuristic is that a component should have one clear job you can state in a sentence: "renders a user's picture at one of three sizes with an optional presence dot."

Counterbalancing this is the real cost of over-nesting. Each layer of nesting adds depth to the layers panel, increases the number of clicks required to reach an override, and adds computational work when Figma re-renders. A chain like Page → Section → Card → Header → Title Row → Badge Group → Badge → Icon Wrapper → Icon is technically valid and practically miserable. Symptoms of over-nesting include designers detaching instances because they cannot find the thing they need to change, sluggish canvas performance on dense screens, and override panels that scroll for pages. Reasonable guidance:

  • Aim for roughly three to four levels of component nesting in most cases; treat five or more as a signal to flatten.
  • Do not create a component for a thing used once — a wrapper frame is sufficient.
  • Avoid wrapper components whose only purpose is to add padding; use auto layout padding on the parent instead.
  • Expose nested properties generously so designers can work from the top level rather than drilling.

Once a set of composed components has stabilised, publishing a team library makes them available beyond the file in which they were built. In the Assets panel, clicking the library icon and then "Publish" pushes the file's components, colour styles, text styles, effect styles, and variables to the team. Other files enable the library and the components appear in their own assets panel, ready to drag onto the canvas. The parent-child relationship persists across files: the main component still lives in the library file, and instances scattered across twenty product files all point back to it.

Using the Assets Panel and Team Library

The assets panel is the left-hand tab beside Layers and Pages. It lists local components (those whose main components live in the current file) and library components (those coming from enabled team libraries), grouped by the slash-notation folders you established. Two controls make it efficient:

  • The search bar filters across all enabled libraries by component name and description. Typing chev surfaces every chevron icon; typing destructive surfaces the destructive button if that word appears in its description even when it is not in the name. Searching and dragging is almost always faster than navigating folders, which is another argument for precise, predictable names.
  • The grid/list toggle switches between visual thumbnails (better for icons and illustrations) and a compact text list (better for scanning a large set of named components).

Components can also be inserted without the panel at all, via the insert menu or the Shift + I shortcut, which opens a searchable resource picker over the canvas.

Crucially, a library is not only components. Colour styles, text styles, effect styles, grid styles, and variables publish alongside components, and this is what turns a component collection into a genuine design system. These shared styles are your design tokens — the named, semantic values that your components reference rather than hard-coding:

Enabling a library in a consuming file is done from the Assets panel's library modal: toggle the library on, and every component and style it contains becomes available in that file's assets panel and style pickers immediately. Designers do not need to copy anything manually; they simply drag instances in. Libraries can be enabled per-file or, for organisation plans, enabled by default across a whole team or organisation.

Updates are deliberately not automatic. When a library maintainer edits a main component and clicks Publish, they are prompted to write a short changelog note, and they can choose which changed items to include in that publish. Consumers of the library then see a notification badge; opening it shows a list of changed components with before/after previews, and the consumer chooses to accept the update — all of it,or individual items. This handshake exists because an unannounced change to a core component can ripple through dozens of screens in the middle of a stakeholder review. Deferring the update lets a designer finish and present their current work, then sync deliberately.

Several consequences follow from this model that are worth internalising:

  • Out-of-date files drift silently. A file whose owner never accepts updates will slowly diverge from the live system. Teams often set a convention such as reviewing library updates at the start of each sprint.
  • Publish notes are documentation. "Increased Button/Primary min height to 44 for accessibility" is far more useful six months later than Figma's default blank note.
  • Deleting a main component does not delete its instances. Existing instances keep rendering, but they become orphaned — they can no longer receive updates and will be flagged as missing. Deprecate rather than delete: rename the component to _Deprecated/Button Old, add a description pointing to the replacement, and remove it only after usage drops to zero.
  • Swapping libraries is possible. Figma can bulk-swap instances from one library to another by matching component names, which is how teams migrate from a legacy system to a new one — and another reason stable, matching names matter.

Putting the whole chain together with a concrete example: you design a search field on a settings screen. You wrap it in auto layout, name the children Icon Leading, Placeholder, and Icon Trailing, apply the colour style Surface/Field/Default and the text style Body/Medium/Regular, and press Ctrl/Cmd + Alt + K. You duplicate it to create focused, filled, error, and disabled versions, combine them as variants under the property State, add a second property Has Trailing Icon as a boolean, and name the set Input/Search. You write a description explaining that the placeholder must describe the searchable scope. You add interactive component wiring so that clicking the default state changes it to focused. You move the set to the Components page, publish the library with the note "Added Input/Search with 5 states", and your teammate working in the mobile file enables the library, types search into the assets panel, and drags in a field that already behaves correctly in their prototype. That is the whole purpose of a component library expressed in a single workflow: define once, use everywhere, change centrally.

Auto-Layout for Responsive Elements

Auto-Layout for Responsive Elements

▶

Auto-layout is the feature that transforms a Figma frame from a static rectangle holding pinned objects into a living container that measures its own contents and reflows them whenever those contents change. Before auto-layout, a designer who wanted a button to grow when its label changed from "OK" to "Confirm payment details" had to manually drag the rectangle, re-centre the text, and nudge every neighbouring element. With auto-layout, the button resizes itself, the row it sits in redistributes its spacing, and the card containing that row grows taller — all in a single keystroke of typing. This behaviour is deliberately modelled on CSS Flexbox, so the mental model you build in Figma transfers almost directly to the code a developer will eventually write. Mastering auto-layout is therefore less about learning a panel of controls and more about learning to think of an interface as a hierarchy of nested stacks, each one with rules about how it distributes space.

What auto-layout actually is. An auto-layout frame is a frame with an added set of layout rules: a stacking direction, a gap between children, padding on each of its four sides, an alignment setting, and sizing behaviour for both the frame itself and each of its children. Children inside an auto-layout frame lose their absolute X/Y coordinates; instead their position is computed from their order in the layer list and the frame's rules. You can see this immediately in the layer panel — reordering a layer inside an auto-layout frame physically moves the element on canvas.

  • Applying it. Select one or more objects and press Shift + A, or use the Auto layout section of the right-hand design panel and click the plus icon. If you select several loose objects, Figma wraps them in a new auto-layout frame and infers the direction from how they are currently arranged — three elements sitting side by side become a horizontal stack, three stacked vertically become a vertical one. If you select an existing frame, that frame itself gains layout rules without a new wrapper being created. Shift + Alt/Option + A removes auto-layout and restores absolute positioning.
  • Direction. The direction control offers horizontal (children flow left to right, equivalent to flex-direction: row), vertical (top to bottom, flex-direction: column), and in current Figma versions wrap, which is a horizontal flow that pushes overflowing children onto a new line, equivalent to flex-wrap: wrap. Wrap unlocks grid-like galleries, tag clouds and chip groups that previously required manual placement.
  • Padding and gap. Padding is the breathing room between the frame's own edge and its children; gap (Figma labels it "spacing between items") is the distance between adjacent children. These two values are what give a component its density and rhythm. A compact data table row might use 8 px padding and a 4 px gap; a marketing hero section might use 64 px padding and a 32 px gap.
  • Frame sizing. Every auto-layout frame's width and height can independently be set to hug contents, fill container, or fixed. This is the single most important concept in the entire feature, and it is covered in detail below.

Sizing modes: hug, fill, and fixed. The width and height fields in the design panel are not just numbers — each has a dropdown that controls how that dimension is calculated. Choosing the right combination for each frame in a hierarchy is what separates a layout that survives real content from one that collapses the first time a product name runs to two lines.

A worked example makes the interplay concrete. Imagine a notification row 360 px wide containing an avatar, a text block, and a timestamp:

Row  (horizontal auto-layout, W: Fixed 360, H: Hug, padding 16, gap 12)
 ├─ Avatar     W: Fixed 40,  H: Fixed 40
 ├─ TextBlock  W: Fill,      H: Hug      (vertical auto-layout, gap 4)
 │    ├─ Title    W: Fill, H: Hug
 │    └─ Message  W: Fill, H: Hug
 └─ Timestamp  W: Hug,       H: Hug

Figma resolves this by first measuring the fixed avatar (40 px) and the hugging timestamp (say 36 px), subtracting the padding (16 + 16) and two gaps (12 + 12), and awarding the remaining 228 px to the text block, which is set to fill. Because the text block has hug height and its children also hug, a longer message wraps to two lines, the text block grows taller, and the row — which hugs vertically — grows with it. Nothing is manually repositioned. Change the avatar to 56 px and the text simply gets 16 px narrower. This is why mixing sizing modes in nested frames is described as the key to responsive layouts: fixed elements claim their space first, hugging elements claim only what they need, and filling elements absorb whatever is left over.

Two practical refinements are worth knowing. First, a child can fill in one axis and hug or stay fixed in the other — a text block typically fills horizontally and hugs vertically. Second, Figma supports minimum and maximum width/height constraints on auto-layout frames. Setting a card to "fill container, max width 480" reproduces the common responsive pattern of a fluid column that stops growing on wide screens, and setting a button to "hug, min width 96" prevents a one-character label from producing an absurdly narrow pill.

Spacing, padding, and alignment. The padding control can be expanded from a single value into four independent inputs (top, right, bottom, left) by clicking the detail icon beside it. This matters more than it sounds: asymmetric padding is extremely common — a list item with 16 px of side padding but only 12 px top and bottom, or a text field with extra right padding to clear a trailing icon. Historically designers faked this by inserting invisible rectangles as "spacers"; those hacks bloated the layer tree, confused developers reading the file, and broke whenever a component was resized. Independent padding inputs eliminate the need entirely, and you should treat any surviving spacer rectangle in a file as a code smell to be refactored out.

  • Gap. One uniform value applies between every pair of adjacent children along the stacking direction. Because it is uniform, if one item in a row needs to sit further away than the others, the correct solution is to group the tighter items into their own nested auto-layout frame with a smaller gap, not to abandon auto-layout.
  • Alignment. A nine-point alignment grid controls how children sit on the cross axis and, when there is leftover space, on the main axis too. For a horizontal row, top, centre and bottom determine vertical placement; for text-heavy containers Figma also offers baseline alignment, which lines up the typographic baselines of mixed-size text rather than their bounding boxes. Baseline alignment is what makes a price like "£49.99/month" sit correctly when the pound figure is 32 px and the suffix is 14 px — centre alignment would make the small text float visibly high.
  • Space between. Setting the gap field to the "space between" option (the icon at the right of the spacing input, or typing auto) changes distribution so that the first child is pushed to one edge, the last to the opposite edge, and any remaining children are spaced evenly between them. This requires the frame to be fixed or filling in the main-axis dimension, because hugging leaves no spare space to distribute. It is the canonical solution for a navigation bar with a logo on the left and account controls on the right, for a card footer with a price on one side and a button on the other, and for a modal header with a title and a close icon.
  • Canvas stacking. When children overlap in a tight horizontal stack (overlapping avatars in a "+3 others" group), the canvas stacking control decides whether the first or last child renders on top — a small but frequently needed touch.

Building reusable list and card patterns. Auto-layout pays its biggest dividends when it is used as the skeleton of repeating UI. Consider three canonical patterns.

The list. Create a frame with vertical auto-layout, width fixed or filling, height set to hug, and a gap of 0 if the rows carry their own dividers or 8–12 px if they are separated cards. Each time you duplicate a row with Ctrl/Cmd + D, the list grows downward and every subsequent element in the parent frame moves down with it; deleting a row closes the gap instantly. Because the list hugs, you never set its height by hand, so an empty state, a three-item state and a forty-item state are all the same frame. Dragging a row up or down inside the list reorders it with a live preview — invaluable when prototyping a reorderable playlist or task list.

The card. A card is usually a vertical auto-layout frame with hug height, fixed or filling width, and generous padding (16–24 px). Inside it sit an image (fixed height, filling width), a text stack (filling width, hugging height), and a footer row (filling width, horizontal, space between). Because the padding is a property of the frame rather than a visual gap you eyeballed, a card with a two-word title and a card with a five-line description have identical internal margins. Set the card's corner radius, fill, and shadow on the frame itself and the whole thing behaves as one responsive object.

The wrapping gallery. Set direction to wrap, give the frame a fixed or filling width, hug height, a horizontal gap of 12 and a vertical gap of 12 (wrap mode exposes both). Drop in twenty filter chips of varying label lengths and they flow onto as many rows as needed; narrow the parent frame and they reflow into more rows while the frame grows taller to accommodate them. Combined with the alignment control, you can decide whether a partially filled final row aligns left, centre, or is spread across the width.

These patterns become genuinely powerful when combined with components and variants. A list-item component with variants for state = default | hover | selected and read = true | false can be dropped repeatedly into a hugging vertical list; switching one instance to "selected" changes its background and leading indicator without disturbing the stack, while switching another to "unread" might reveal a dot and switch the title to semibold. Because the list is auto-layout, any size difference caused by that change is absorbed automatically.

Auto-layout and component interaction. Components and auto-layout are complementary systems, and the interesting behaviour happens where they meet. When a variant swap shows or hides a nested element — revealing a trailing icon, adding a badge, switching a one-line title for a two-line one — the parent auto-layout frame recalculates its size immediately, and that recalculation propagates up the entire hierarchy. A button that gains a leading icon gets wider; the toolbar row it lives in redistributes; the card hugging that toolbar grows. You can also toggle a layer's visibility directly on an instance (the eye icon in the layer list), and because hidden layers are excluded from auto-layout measurement, the container closes up as though the layer never existed. This is the mechanism behind "optional slot" components: build the maximal version once, then hide what each instance does not need.

  • Text overrides. Overriding a label on an instance is the most common content change of all, and auto-layout guarantees it is safe. Because the padding and gap are rules rather than measured pixels, a label changing from "Save" to "Save and continue to checkout" produces a wider button with identical internal spacing. The discipline this demands is that text layers inside components should be set to auto width (so the parent hugs) or fill container with auto height (so it wraps) — never fixed size, which would clip or stretch the override.
  • Nested instances. An instance placed inside an auto-layout frame behaves like any other child: it can fill, hug or be fixed. A common production pattern is a row component whose first slot is an instance-swappable icon placeholder at a fixed 24 × 24, followed by a filling text instance. Swapping the icon never shifts the text's left edge because the slot's size is fixed.
  • Why this is "production-ready". Combining auto-layout with variants means a single component can represent every state and every content length your product will ever encounter, and the prototype will render each one correctly without manual repair. This is the foundation of data-driven prototyping: you can paste real copy, real names, and real prices — or use Figma's content plugins to inject them — and the interface absorbs them. It is also what makes handover meaningful, because the hug/fill/fixed decisions map directly onto the Flexbox rules a front-end developer will implement.
  • Stress-test with realistic content. Before any usability test or critique, deliberately push the extremes: the longest plausible product name, a German or Finnish translation (typically 30% longer than English), a user with a single-character display name, a zero-item empty state, and a forty-item overflow state. Problems surface fast — a fixed-width label that clips, a row that wraps to three lines and breaks vertical rhythm, a price that collides with a button because the row was never set to space-between. Fixing these before evaluation prevents participants from reporting layout bugs instead of genuine usability issues, and it protects the credibility of the prototype in front of stakeholders.

Common pitfalls. Three mistakes account for most auto-layout frustration. First, over-nesting: every grouping should earn its place, because deep hierarchies are hard to edit and hard to read in handover. Second, fighting the system by leaving one stray fixed-width element in an otherwise fluid chain — the chain is only as responsive as its least flexible link. Third, forgetting that absolute position exists: for genuinely overlapping elements such as a notification dot on an avatar or a floating action button over a list, you can mark a child as absolutely positioned so it is ignored by the layout calculation while still being clipped and moved by its parent. Using it sparingly and intentionally is correct; using it to escape layout rules you have not understood is not.

Interactive Prototyping and Connections

▶

A static set of screens, no matter how carefully composed, can only ever answer questions about appearance. The moment you want to know whether a user understands where to tap, whether a transition feels abrupt, or whether a modal interrupts the task at the wrong moment, you need motion and consequence. Figma's prototyping layer supplies exactly that: a system for wiring frames together with triggers, actions, destinations, and animations, so that a collection of artboards behaves like a working interface. Crucially, prototyping in Figma is non-destructive and lives alongside your design work — the connections you draw are stored as properties of layers, not as separate files, so a change to a button's visual design automatically carries through to every interaction attached to it. This topic walks through the prototype panel itself, the vocabulary of triggers and actions, the transition and easing models, scroll and fixed-position behaviour, overlay patterns, and finally how to preview, present and share the result for evaluation.

The Prototype Panel Overview. Figma's right-hand sidebar operates in two modes, selected by the tabs at the top: Design and Prototype. Clicking the Prototype tab does not change your canvas — the same layers, frames and components remain visible — but it swaps the sidebar's contents from visual properties (fill, stroke, effects, constraints) to interaction properties, and it reveals the connection arrows drawn between frames. This mode switch is the single most important orientation point for beginners: if you cannot find the "Interactions" list or the "Flow starting point" button, you are almost certainly still in Design mode.

Once in Prototype mode, selecting any frame, group, component instance or even a single shape causes a small circular interaction handle to appear on the right edge of the selection's bounding box. Hovering over the selection makes this handle a saturated blue node; clicking and dragging from it pulls out a connection line, sometimes called a "noodle". Dropping that line onto another frame creates an interaction and opens a floating details popup where you set the trigger, the action and the animation. Dropping it onto empty canvas offers to create a new destination frame. You can also create an interaction entirely from the sidebar by clicking the + next to "Interactions", which is useful for actions that have no visual destination, such as Back, Close overlay, or Open link.

The panel itself is organised top to bottom in a predictable way. When a top-level frame is selected you see: the Flow starting point control (with a flow name and optional description), the list of Interactions attached to that frame, Scroll behaviour (overflow direction and position fixing), and Prototype settings — which in turn contain the device, model, orientation, and background colour used when the prototype is played. When a child layer is selected (a button, a card, an icon) the panel narrows to that layer's interactions plus its scroll/fix options. Interactions are listed as human-readable summaries such as On click → Navigate to Checkout, and clicking one reopens the details popup for editing. Hovering an interaction row exposes a minus icon for deletion, and selecting a connection line on the canvas and pressing Delete achieves the same thing.

Device and background settings deserve more attention than they usually get. The Device dropdown (Phone, Tablet, Desktop, Watch, Presentation, or None) and the Model dropdown (e.g. iPhone 14 Pro, Pixel 7, Surface Pro) draw a realistic chrome around the prototype in Presentation view. Choosing a device whose pixel dimensions match your frame size is important: if your frames are 390 × 844 but you select a 360 × 800 model, Figma will scale the prototype to fit and your type will no longer be rendered at true size, which undermines any judgement about legibility. The Background colour fills the area around the device frame; a neutral mid-grey is a sensible default for usability sessions because it avoids both the glare of pure white and the dramatic contrast of black, neither of which represent how the product will actually be seen.

Triggers and Actions. Every Figma interaction is a sentence with two mandatory parts and several optional ones: when this happens (the trigger), do this (the action), to this target (the destination), using this animation (the transition), and sometimes with these extra settings (delay, easing, overlay position). Separating trigger from action is the conceptual key — the same action can be fired by different triggers, and the same trigger can fire different actions on different elements.

  • On click / On tap — the workhorse. Figma shows "On click" when the prototype device is set to Desktop and "On tap" when it is a phone or tablet, but internally it is the same trigger; a mouse click and a finger tap both satisfy it. Use it for buttons, list rows, nav items and anything the user deliberately activates.
  • On hover — fires while the pointer rests over the element and automatically reverses when the pointer leaves. It is only meaningful for pointer-driven products; on touch devices there is no hover state, so a hover-only affordance is an accessibility failure. Typical use: desktop menu reveals, tooltip previews, card lift effects.
  • While pressing — holds the destination state only while the mouse button or finger is down, reverting on release. Good for simulating pressed button states, press-and-hold previews, or "peek" interactions.
  • On drag — fires when the user drags anywhere on the element in any direction. Combined with Smart Animate it produces convincing bottom-sheet pulls, swipe-to-delete rows, and carousel swipes. Figma also exposes directional drag variants (drag left, right, up, down) through the trigger dropdown in newer versions.
  • After delay — only available on frames, not on child layers. The interaction fires automatically a set number of milliseconds after the frame appears. It is the standard way to simulate loading spinners, splash screens, auto-advancing carousels and toast messages that dismiss themselves. A delay of 0 ms creates an immediate redirect, which is handy for building a "router" frame.
  • Key/gamepad — binds a keyboard key or controller button to an action, useful for desktop app prototypes, kiosk software and accessibility demonstrations (for example, pressing Esc to close a modal).
  • Mouse enter / Mouse leave / Mouse down / Mouse up — the "advanced" set. Unlike On hover and While pressing, these do not automatically reverse, so you must wire the return interaction yourself. This gives precise control, for example making a dropdown open on Mouse enter and close only on a click elsewhere.

Navigate to is the one students reach for first, and it is correct for genuine page changes: tapping a product card to reach a product detail screen, submitting a form to reach a confirmation screen. Because it pushes onto history, a later Back action will unwind it correctly, which is what makes browser-like and app-like navigation feel natural. A common beginner error is to wire a "back" arrow with Navigate to pointing at the home screen; this works visually but corrupts the history stack, so a subsequent Back behaves unexpectedly. Use the dedicated Back action instead.

Open overlay is the correct choice whenever the underlying context must remain visible and in place. The essential difference is state preservation: if a user has scrolled a long list halfway down and then opens a filter panel as an overlay, closing the filter returns them to exactly the same scroll position, because the base frame was never unmounted. Had you used Navigate to on a full-screen copy of the list with the filter drawn on top, you would need a duplicated frame and the scroll position would reset. Overlays therefore reduce frame count and increase realism simultaneously.

Scroll to operates inside a single frame rather than between frames. You select a target layer within the same scrolling frame — a section heading, an anchor marker, a form field — and Figma scrolls the viewport so that layer comes into view. You can choose whether the movement is animated and add an offset so the target does not sit flush against a fixed header. Classic applications include a long landing page with a sticky navigation bar whose links jump to "Features", "Pricing" and "FAQ", or a "Back to top" button at the foot of an article. A practical tip: give your anchor targets clear names such as anchor/pricing so they are easy to find in the destination dropdown.

Transitions and Animation. Once trigger, action and destination are set, the Animation section of the interaction popup determines how the change is rendered. The choice is not cosmetic — transition style communicates spatial relationships and causality, and the wrong one makes an interface feel either sluggish or disorientating.

  • Instant — the destination replaces the origin with no animation at all. This is the honest default for early, low-fidelity click-through prototypes where you are testing information architecture and task flow rather than polish. It is also the fastest to review, because no time is spent waiting for motion, and it avoids the risk of testers commenting on animation when you wanted feedback on structure.
  • Dissolve — a cross-fade between the two frames over a set duration. Because a fade implies no spatial direction, it suits changes that are not "somewhere else": opening a modal, switching between unrelated tabs, revealing a full-page takeover, or showing a loading state becoming content. Durations of roughly 150–300 ms feel responsive; beyond about 400 ms a dissolve starts to feel like lag.
  • Move in / Move out / Push / Slide in / Slide out — directional transitions that convey hierarchy. Push moves the outgoing screen off as the incoming screen arrives, mimicking native stack navigation (push right-to-left to go deeper, left-to-right to come back). Move in slides the new screen over a stationary base, which suits side drawers and bottom sheets.
  • Smart Animate — the most powerful option. Figma compares the layers in the origin frame and the destination frame and, wherever it finds layers with identical names at the same position in the layer hierarchy, it interpolates their properties: position, size, rotation, opacity, fill colour, corner radius, stroke weight and more. Layers present in one frame but not the other are faded in or out. The result is that two still frames become a continuous micro-interaction without any timeline editing.

Smart Animate rewards disciplined naming. Suppose you build a card that expands into a detail view. In Frame A the card contains layers named cover, title and meta; in Frame B you duplicate that card, enlarge cover to full width, move title up and add a new body paragraph. Because cover, title and meta keep their names, Smart Animate will grow, move and recolour them smoothly, while body simply fades in. If you had instead deleted and redrawn the cover image, it would be named Rectangle 47 in one frame and Image 3 in the other, and Smart Animate would cross-fade them rather than morph them — the classic symptom of "my Smart Animate isn't working". The workflow rule is therefore: duplicate the frame, then modify; never rebuild.

Two further Smart Animate options are worth knowing. Smart Animate matching layers is the standard mode described above. Animate matching layers can also be combined with Move/Push/Slide transitions, so the screens slide while shared elements morph — ideal for a hero image that travels from a list into a detail page while the rest of the content pushes in from the right. And because Smart Animate interpolates component variants too, a Change to action between variants of the same component produces smooth toggles, loading bars and animated icons with no frame duplication at all.

Easing governs the velocity profile of the animation and is where a prototype gains or loses credibility. Linear motion moves at a constant speed and reads as mechanical, because nothing in the physical world starts and stops instantaneously. The standard set is:

Spring curves differ from bezier curves in an important way: they are defined by physical parameters rather than by a fixed duration, so the animation ends when the simulated motion settles. This makes them especially suitable for gesture-driven interactions, where the user's drag velocity should carry into the release. A practical heuristic for duration: 100–150 ms for small state changes such as a button press, 200–300 ms for most screen transitions, and 300–500 ms for large, full-screen or hierarchy-changing moves. Anything longer than about 500 ms will be perceived as waiting, not as feedback.

Scrollable Frames and Fixed Elements. Real screens are taller than the device viewport, and simulating that difference is one of the quickest ways to make a prototype feel authentic. In Figma the mechanism is deliberately simple: the frame defines the viewport, and anything extending past the frame's edges becomes scrollable content, provided two conditions are met. First, the frame must have Clip content enabled in the Design panel, so overflowing content is hidden rather than spilling onto the canvas. Second, the frame's Overflow behaviour in the Prototype panel must be set to Vertical, Horizontal, or Both directions rather than No scrolling.

Concretely: if you create a frame sized 390 × 844 to represent a phone screen and then place a content column 390 × 2400 inside it, the visible 844 pixels are the viewport and the remaining 1556 pixels become scroll range. Figma computes the scrollable extent automatically from the bounding box of the frame's children — you never set a scroll height manually. A frequent source of confusion is an invisible stray layer (an old guide rectangle, a hidden note) sitting far below the content; because it contributes to the bounding box, the prototype scrolls into a large empty void. Checking the layer list for strays is the standard fix.

Fixed elements are the counterpart to scrolling. Selecting a child layer of a scrolling frame and enabling Fix position when scrolling in the Design panel (position section) pins it to the viewport, so it remains in place while everything else moves. Figma automatically moves fixed layers to the top of the layer order within the frame so they render above the scrolling content. The canonical uses are a sticky app bar at the top, a tab bar or navigation bar at the bottom, a floating action button in the lower-right corner, and a persistent "Add to basket" price bar on an e-commerce product page. Combining fixed elements with constraints matters too: a bottom tab bar should be fixed and constrained to the bottom edge so that it behaves correctly if the frame is resized for a different device.

A more advanced pattern is nested scrolling. Place a horizontally scrolling frame inside a vertically scrolling frame and you reproduce the familiar streaming-service layout: the page scrolls up and down through categories, while each category row scrolls sideways through titles. For this to work, the inner frame must itself clip content and have horizontal overflow enabled, and its content row must be wider than the inner frame. Horizontal scrolling is the right tool for carousels (promotional banners, onboarding slides), gallery rows (film posters, product thumbnails), chip and filter strips, and scrollable tab bars where there are more tabs than fit the width. In every case, leave a partially visible item at the right edge — a "peek" of 16–24 px — because that visual cut-off is the affordance that tells users more content exists.

Finally, note the interaction between scrolling and navigation. By default, Figma preserves scroll position when navigating between frames if the destination has a matching scroll container and the "Preserve scroll position" option is checked in the interaction popup. This is how you simulate a tab bar: tapping between "Home", "Search" and "Profile" keeps each tab's scroll position intact, exactly as a native app would.

Overlays and Modal Patterns. An overlay is any frame drawn on top of the current screen rather than replacing it. You create oneby selecting a trigger element, dragging its connection handle to the target frame, and then changing the action from Navigate to to Open overlay. As soon as you do, the interaction popup expands to reveal overlay-specific settings: position, background dimming, close-on-click-outside, and whether the overlay should animate in.

The target frame should be sized to the overlay itself, not to the whole screen. A confirmation dialog might be a 320 × 180 frame; a bottom sheet might be 390 × 420; a dropdown menu might be 200 × 240. Building the overlay at its true size is what allows Figma to position it correctly and to dim everything around it. A common mistake is to draw the dialog inside a full-screen frame with a transparent background — this works, but it disables Figma's own dimming and positioning controls and makes the overlay harder to reuse.

Manual positioning is the option students under-use. When you choose Manual, Figma shows a ghost of the overlay on the current frame so you can drag it until it sits directly beneath the menu button or beside the help icon that opens it. Because the offset is stored per interaction, the same overlay frame can be reused by several triggers at different positions — one dropdown component serving the "sort", "filter" and "view" buttons on a toolbar, for instance.

Background dimming (the "Add background behind overlay" checkbox, with an adjustable colour and opacity) places a semi-transparent scrim between the base screen and the overlay. Its purpose is both aesthetic and functional: it reduces the visual competition of the content behind, signals that the underlying screen is temporarily non-interactive, and reinforces the sense of a layer stacked in front. A black scrim at 20–50% opacity is the conventional range; lighter values suit light-mode dropdowns, heavier values suit full-attention dialogs. Alongside the scrim sits the Close when clicking outside option, which lets the user dismiss the overlay by tapping the dimmed area. Enable it for dismissible, low-stakes overlays such as menus, sheets and image viewers; disable it for destructive confirmations ("Delete account?") where an accidental tap outside should not count as a decision.

Overlays can animate just like frame navigations. A bottom sheet is most convincing with Move in → from bottom and an Ease Out or Gentle Spring curve; a centred dialog usually reads best with Dissolve at around 200 ms, sometimes combined with a slight scale-up built using Smart Animate between two variants. Remember to wire the matching exit: a Close overlay action with Move out → to bottom so the sheet leaves the way it arrived. Mismatched entry and exit animations are one of the most noticeable signs of an unpolished prototype.

Because overlays are themselves frames, they can contain their own interactive content — buttons, inputs, scrollable lists, even nested overlays. This enables genuine multi-step modal flows. Consider a "Book an appointment" dialog with three stages: choose a service, choose a time, confirm. Rather than navigating away from the page behind, you build three overlay frames and wire the "Next" buttons with Swap overlay, which replaces the current overlay with the next one while leaving the base screen and its scroll position untouched. Adding Smart Animate to the swap makes the dialog appear to resize and its content to slide, exactly like a real wizard. A "Cancel" button on any step uses Close overlay to return the user to the page beneath.

Two practical cautions. First, overlays stack: opening an overlay from within an overlay leaves both mounted, and Close overlay dismisses only the topmost one, so a three-deep stack needs three closes (or a Close all overlays where available). Keep stacks shallow. Second, a scrollable overlay needs its own clip and overflow settings; a long terms-and-conditions sheet must be a clipped frame with vertical overflow, otherwise the content simply extends beyond the viewport and cannot be reached.

Previewing and Sharing the Prototype. Building interactions is only half the work; the point of a prototype is that other people run it. The Play button (the triangle icon in the top-right of the toolbar) launches Presentation view in a new browser tab, rendering the prototype inside whatever device and background you configured in Prototype settings. The keyboard shortcut is Ctrl/Cmd + Alt + Enter, and Shift added to the play action restarts from the first frame of the current flow. Presentation view hides the canvas, layer list, sidebars and rulers entirely, showing only the artefact — which matters in testing, because a participant who can see your layer names and messy canvas will comment on the construction rather than the experience.

Inside Presentation view a small toolbar offers controls worth demonstrating to testers and stakeholders:

  • Options / Fit — choose Fit width, Fit height, Actual size or Fill. "Actual size" is the honest setting for evaluating tap target sizes and type legibility.
  • Show hotspot hints — pressing the keyboard shortcut Ctrl/Cmd + / or clicking anywhere on a non-interactive area flashes blue highlights over every clickable region. Useful for debugging, but switch it off during usability testing: revealing the hotspots destroys the very discoverability question you are trying to answer.
  • Restart — returns to the flow starting point and clears history, which is how you reset between participants.
  • Comments — reviewers can pin feedback directly onto a screen in the prototype; those comments appear back in the editor file anchored to the same place.
  • Flows list — if the file contains several named flows, viewers can jump between them from a sidebar without needing separate links.

The flow starting point determines where the preview begins. Select a top-level frame in Prototype mode and click the + beside "Flow starting point"; a labelled flag appears above the frame on the canvas and the frame is registered as an entry screen. Flows should be named meaningfully — "01 Onboarding", "02 Search and filter", "03 Checkout" — and may carry a description that is displayed to viewers in Presentation view, which is an excellent place to write the task instruction for a test ("You want to find a vegetarian recipe under 30 minutes and save it"). A file may contain many flows; multiple flows let you test discrete tasks without forcing participants through unrelated screens first. If no starting point is set, Figma simply begins at the top-left-most frame on the page, which is rarely what you intend.

Sharing is handled through the blue Share button. The dialog distinguishes between inviting named collaborators by email and generating a general access link. Setting the link to Anyone with the link → can view produces a URL that requires no Figma account, which is essential for remote testing with external participants. Copying the link from inside Presentation view (or using Copy link in the share dialog while a prototype is open) yields a /proto/ URL that opens directly in prototype mode at the chosen flow, rather than a /file/ URL that drops people into the editor. The difference matters: the editor link exposes your working canvas and will confuse non-designers.

Two further delivery options complete the picture. The Figma Mirror app streams the prototype from your desktop file to a physical phone or tablet over the same account, so you can judge real tap target sizes, thumb reach and perceived animation speed on actual hardware — a 44 × 44 pt button that looks generous on a 27-inch monitor can feel cramped in the hand. And embedding the prototype with an <iframe> snippet from the share dialog lets you place a live, interactive version inside a case study, portfolio page or documentation site.

Before any evaluation session, run a short pre-flight check: play the prototype from the intended flow start, walk the happy path end to end, deliberately tap items you have not wired to see whether dead ends trap the user, confirm that every modal can be closed, verify that back navigation behaves, test the share link in a private browser window to confirm anonymous access, and switch hotspot hints off. Ten minutes of this discipline prevents the most common failure of prototype-based testing, which is a participant stalling on a broken link and the session degenerating into a debugging exercise.

A static set of screens can show what an interface looks like, but it cannot show how it behaves. Figma's Prototype tab is where you turn frames and components into something a person can actually click through: you select a layer, drag a connection to a destination, and then specify the trigger (what the user does), the action (what the prototype does in response), and the animation that carries the change on screen. Once those connections exist, you can run the file in Presentation mode and share a link so reviewers and usability-test participants can explore the flow on their own.

In this course, prototyping is how your design becomes testable. Evaluation methods you study later — heuristic walkthroughs, think-aloud sessions, task-based testing — all depend on a prototype that responds realistically enough that users forget they are looking at a mockup. Details matter here: a modal that appears over its parent screen, a list that scrolls while the navigation bar stays fixed, a button that visibly changes on hover. These are the affordances and feedback cues users rely on, and in Figma you have to wire them deliberately.

The three videos below come from Figma's own channel and move from building reusable interactive components, to timing-based transitions that run without user input, to overlay behavior for things like modals and expanding thumbnails. As you watch, pay attention to which trigger each presenter chooses and why, how the animation type (instant, dissolve, smart animate, move in) changes the perceived meaning of a transition, and how a small amount of setup in a component can remove dozens of repetitive connections from your file. Try to rebuild at least one example yourself rather than only watching.

High-Fidelity Design and Visual Polish

1

High-Fidelity Design and Visual Polish

▶

High-fidelity design is the stage at which a structural wireframe — grey boxes, placeholder labels and rough spacing — becomes a convincing representation of a real, shippable product. The underlying layout usually does not change much; what changes is the visual language applied to it: a defined colour palette, a disciplined type scale, real or realistic imagery, consistent iconography, and carefully judged depth effects. The purpose is not decoration for its own sake. A high-fidelity mockup lets stakeholders evaluate brand fit, lets usability testers react to the interface as they would to a real app, and lets developers read exact values (hex codes, font sizes, corner radii, shadow offsets) straight from the file. In Figma, the mechanism that makes this polish sustainable rather than chaotic is the style: a named, reusable definition of a colour, a text treatment, an effect, or a grid. Working with styles turns a collection of individually painted rectangles into a coherent, centrally governed design system.

Before touching any visual property, it is worth adopting a working rule: if a value appears more than once, it should be a style. A hex code typed manually into twelve buttons is twelve separate maintenance jobs; the same colour stored as Brand/Primary is one. The sections below work through each category of visual property, how Figma implements it, and the conventions that keep a high-fidelity file maintainable as it grows.

Defining and applying colour styles. A colour style in Figma is a saved paint definition that can be reused on any fill or stroke. To create one, select an element that already has the fill you want, open the Fill section of the right-hand design panel, and click the four-dot style icon that sits to the right of the fill row. Figma offers a dialog where you name the style and optionally add a description — the description field is where you record usage guidance such as “Primary actions only; do not use for body text.” Once saved, the style appears in the document's local styles list and can be applied to any other object by selecting it, clicking the same four-dot icon, and choosing the style from the picker. Styles can also be created from the Local Styles section of the design panel when nothing is selected, which is useful when you are defining a palette up front rather than harvesting it from existing work.

The single most important decision is naming. Figma treats the forward slash as a folder separator, so a name like Brand/Primary creates a group called Brand containing an entry called Primary. This turns a flat alphabetical list of forty swatches into a browsable, self-documenting hierarchy. The convention that scales best is a token hierarchy: group by role rather than by appearance. A style called Feedback/Error survives a rebrand because the role (error messaging) does not change even if the value moves from #D32F2F to #B3261E. A style called Red or Red-2 becomes a lie the moment the colour changes, and it tells a teammate nothing about when to use it.

The payoff arrives when something changes. Because every object referencing Brand/Primary holds a link to the style rather than a copy of the value, editing the style updates every instance across every frame and page in the file instantly. Suppose a client reviews the mockup and decides the blue is too cold. You open Local Styles, click the edit icon beside Brand/Primary, drag the colour picker a few degrees warmer, and the forty-one buttons, six active tabs, nine icons and three progress bars that use it all shift together. The alternative — selecting objects one by one, or using Select All With Same Fill and hoping nothing was slightly off by a digit — is the scenario that produces hi-fi files where six nearly identical blues coexist. If an element is intentionally not on-system, that should be a conscious, documented exception.

Colour styles are not limited to flat colour. The paint type dropdown lets a style store a linear, radial, angular or diamond gradient, and a gradient saved as a style behaves exactly like a solid one. This matters for high-fidelity work because gradients do a lot of expressive heavy lifting: a Gradient/Hero style for a marketing header, a Gradient/Scrim style running from rgba(0,0,0,0) at the top to rgba(0,0,0,0.7) at the bottom, laid over a photograph so white caption text stays legible regardless of what is in the image. The scrim example also illustrates that a colour style carries its opacity as part of the definition, so semi-transparent overlays, disabled-state washes and hover tints are all expressible as reusable tokens rather than one-off alpha values typed into the opacity field.

A practical note on accessibility: define contrast into the palette rather than checking it afterwards. Pair every background style with the text styles that are legal on top of it, and verify ratios against WCAG (4.5:1 for body text, 3:1 for large text and meaningful UI boundaries) using a plugin such as Stark or Contrast. Doing this at the style level means the whole file inherits compliant combinations; doing it per-screen means auditing the same decision fifty times.

Typography styles and text hierarchy. A text style bundles font family, font weight/style, size, line height, letter spacing, paragraph spacing, text case and text decoration into one named definition. Creating one follows the same mechanic as colour: style a piece of text the way you want it, then click the four-dot icon beside the Text section in the design panel and give it a name. Note that a text style deliberately does not include colour — colour comes from a separate fill style. This separation is a feature, not an oversight: it lets you apply Heading/H2 to a heading that is Neutral/900 on a light screen and Surface/Card (white) on a dark hero, without needing two heading styles.

Applying a text style decouples the visual appearance of text from its content. The words inside a frame can be rewritten, translated, or replaced with real copy from the client, and the typography does not drift. Equally, the type system can be revised globally: if user testing shows body copy at 14 px is straining on mobile, you edit Body/Regular once to 16 px with a 24 px line height and every paragraph in the file reflows. Without styles, the same change is a multi-hour sweep with a high chance of missing something.

The deeper design purpose of a type system is hierarchy — the deliberate ordering of information so a user's eye lands on the right thing first, second and third. Hierarchy is produced by contrast across several dimensions at once: size, weight, colour/value, spacing, and case. A page title at 32 px semibold in near-black sits unambiguously above a 16 px regular body paragraph in mid-grey, which in turn sits above a 12 px uppercase caption in light grey with wide letter spacing. A common beginner failure is to build hierarchy from size alone, producing six levels that are each two pixels apart — the differences are too small to read as distinct ranks, so everything flattens into noise. A useful discipline is to limit yourself to roughly five or six text styles for a product screen and make the steps between them obvious. Modular scales (for example, a 1.25 ratio: 12, 14, 16, 20, 25, 31, 39) give mathematically harmonious steps, but a hand-tuned scale rounded to whole pixels and multiples of four is usually more practical for implementation.

Figma supports both Google Fonts and locally installed fonts. The entire Google Fonts catalogue is available natively in the browser version — type Inter, Roboto, Source Sans 3 or Lora into the font field and it resolves with no installation step, which is why Google Fonts are the pragmatic default for student and prototype work: anyone who opens the file sees the same thing. Licensed or system fonts installed on your machine appear too, but only if you are using the desktop app or have the Figma font helper installed on your computer. The important caveat is portability: if you build with a locally installed foundry font and a collaborator does not own it, Figma shows a "missing font" warning and substitutes a fallback, which quietly breaks line lengths and vertical rhythm across the file. For a shared or submitted project, either use a webfont everyone can access or document the font dependency explicitly. Line height is worth a final word: set it as a unit value (for example 24) or a percentage rather than leaving it on Auto, because Auto varies between typefaces and makes vertical spacing unpredictable when you later swap fonts.

Working with images and fills. In Figma, an image is not a separate object type — it is a fill applied to a shape or frame. To apply one, select the target element, open the Fill section, click the colour swatch to open the paint picker, and change the paint type dropdown from Solid to Image; you can then choose a file from disk or drag one straight onto the canvas. Because the image is a fill, it inherits the shape's geometry: drop a photo into a circle and you get a circular avatar; drop it into a frame with a 16 px corner radius and you get a rounded card hero with no masking required. You can also stack an image fill under a gradient fill on the same object to build a scrim in one layer rather than two.

How the image behaves inside its container is governed by the fill mode dropdown:

The same paint popover exposes per-image adjustments — exposure, contrast, saturation, temperature, tint, highlights and shadows — which are useful for making a set of mismatched stock photos read as one coherent library, for example by desaturating everything slightly and pulling the temperature consistently warm. To re-crop or reposition an image after placement, select the element and click the Edit image button that appears in the toolbar (or double-click into the fill), which puts you into a mode where you can drag the crop handles and nudge the image within its frame.

For placeholder imagery, sourcing matters both legally and practically. The Unsplash plugin runs inside Figma and drops royalty-free photographs directly into the selected shape — select six card thumbnails at once, run the plugin, and it fills each with a different image from a search term such as "architecture" or "food". Comparable plugins include Pexels, Content Reel (which supplies names, avatars and text strings as well as images) and Lorem Ipsum generators for body copy. Using real-looking content rather than grey boxes is genuinely important in hi-fi work: it exposes layout problems that wireframes hide, such as what happens when a product name runs to three lines, when a photo is overwhelmingly dark behind white text, or when a user has no avatar at all. Keep file weight in mind too — a dozen 4000 px photographs will make a prototype sluggish, so downscale assets to roughly twice their displayed size before importing.

Icons and vector assets. Icons carry an outsized share of an interface's clarity and personality, and they must be handled as vectors rather than bitmaps. When an SVG is imported into Figma — by dragging the file onto the canvas, or by copying SVG markup and pasting it directly — Figma parses it into editable vector paths inside a frame or group. You can select individual nodes with the pen/vector edit tool, change stroke weights, boolean-combine shapes, and scale the icon from 16 px to 160 px with no loss of crispness, because the renderer redraws the maths at every size rather than resampling pixels. A PNG icon does none of this and will look soft on high-density displays.

Rather than drawing icons from scratch, most projects draw on a community library. Plugins such as Material Symbols/Material Icons, Feather, Iconify (which aggregates hundreds of open sets), Phosphor and Font Awesome let you search by keyword and insert an icon onto the canvas in one click. The critical discipline is to pick one family and stay in it: Material icons are filled and geometric with a particular optical weight, Feather icons are 2 px-stroke outlines on a 24 px grid, and mixing the two produces a subtly incoherent toolbar even if a non-designer cannot say why. Check that your chosen set covers every concept you need before committing, and keep the icon grid consistent — a 24 px frame with a 20 px live area is a common standard, giving icons uniform optical size regardless of whether they are wide (a horizontal menu) or tall (an exclamation mark).

Alignment is where icons most often go wrong, and auto layout is the fix. Placing an icon and a text label inside a horizontal auto-layout frame with a defined gap and vertical alignment set to centre guarantees that the icon stays optically aligned to the text baseline area and that the gap never drifts when the label changes length. A button built this way — auto layout, 12 px horizontal padding, 8 px gap, icon + Label/Button text — resizes itself correctly for "Save", "Save changes" and "Save and continue to payment" with no manual nudging. The same applies to list rows, nav items, chips and input fields with leading icons. Without auto layout, every icon is a floating object whose position must be checked by eye on every screen.

Finally, icons should be coloured with styles, not hard-coded fills. Flatten or union an icon's paths so it has a single fill where possible, then apply Neutral/600 for default states and Brand/Primary for active states. When the brand colour changes, every icon in the file recolours along with the buttons and links, keeping the whole interface in step. Combined with Figma components and variants, this gives you one Icon component whose colour and size are controlled centrally — the foundation of a genuinely maintainable icon system.

Effects: shadows, blurs and overlays. Effects supply depth, separation and focus. Figma's Effects section offers drop shadow, inner shadow, layer blur and background blur, and multiple effects can be stacked on a single object. A drop shadow is defined by five parameters, and understanding each is what separates a believable elevation from a muddy grey smear:

X offsetHorizontal displacement of the shadowUsually 0 in UI, since the implied light source is directly overhead

BlurSoftness of the shadow edgeRoughly 2–3× the Y offset; harder shadows read as closer to the surface

The single biggest improvement most students can make to shadow quality is to stack multiple layers. Real shadows are not one uniform blob: they have a tight, relatively dark contact shadow immediately beneath the object and a broad, very faint ambient shadow spreading further out. Reproducing that with two or three stacked effects produces far more convincing elevation than a single setting. A typical raised card might use:

The last example shows a second use of the drop shadow: with zero blur and a positive spread, it becomes a soft outer ring, which is how focus states and selection halos are typically built. Giving the shadow a brand-tinted colour rather than black, and stacking a tight white inner shadow on a dark surface, are further techniques for making elements feel physically present.

Background blur is a distinct effect that blurs whatever is behind a frame rather than the frame's own contents, producing the frosted-glass look used in iOS navigation bars, macOS sidebars, sticky headers and modal scrims. For it to work, two conditions must hold: the frame carrying the effect must have a fill with less than 100% opacity (a white fill at 60–80% is typical), and there must be content positioned beneath it in the layer order. A header built as a frame with Surface/Card at 70% opacity plus a 20 px background blur will blur the photographs and text scrolling under it, keeping the nav labels legible without hiding the content entirely. Layer blur, by contrast, blurs the object itself and is used for out-of-focus decorative shapes, soft gradient "blobs" behind hero content, or simulating a defocused background state while a dialog is open. The two are frequently confused; the test is simple — layer blur makes the thing you selected fuzzy, background blur makes everything behind it fuzzy.

Just as with colour and type, effects should be saved as effect styles wherever they recur. Select an object with the finished stack of shadows, click the four-dot icon beside the Effects section, and name it by elevation role rather than by its values — Elevation/01 Card, Elevation/02 Dropdown, Elevation/03 Modal, Effect/Focus Ring, Effect/Glass Blur. A role-based elevation ladder of three or four steps is far better than ad-hoc shadows, because it encodes a consistent spatial model: everything at the same conceptual height casts the same shadow, so users learn to read depth as meaning (this card is interactive and sits above the page; this dialog sits above everything and blocks interaction). When a reviewer decides the whole interface feels too heavy, you edit four styles instead of hunting through two hundred objects.

Building and Submitting the Group Project Prototype

1

Building and Submitting the Group Project Prototype

▶

The final stage of a prototyping module is where every isolated skill — frames, components, auto-layout, styles, and interactive connections — stops being an exercise and becomes a deliverable. Building a group project prototype is as much a coordination problem as a design problem. A single designer working alone can tolerate an untidy file because they hold the structure in their head; a team of four cannot. The moment three people are editing the same Figma file, the cost of an undocumented decision, a detached component, or an unassigned screen multiplies. This topic walks through a complete delivery process: defining what must be built, dividing it safely, checking it against an agreed standard, preparing it for outside eyes, running a structured peer evaluation, and closing the loop with documented iteration.

The underlying discipline is simple to state and hard to practise: decide before you build, build to the decision, and verify against the decision. Most group prototypes that fail at submission do not fail because the visual design is poor. They fail because two people built the same screen differently, a flow dead-ends halfway through checkout, or the shared link opens on an arbitrary frame in the middle of the file. Each section below targets one of those failure modes.

Project Scope and Screen Inventory

A screen inventory is a written list of every frame the prototype requires, with each frame tied explicitly to a user task. It is the contract between the team and the brief. Without it, scope expands silently — someone adds a "settings" screen nobody asked for while the core booking flow is still missing two steps.

The inventory should be built from flows, not from a wishlist of pages. Start by writing the user tasks the prototype must demonstrate ("a user signs in and books a class", "a user cancels an existing booking"), then decompose each task into the screens required to complete it. Every frame in the inventory must answer the question: which task does this serve, and what comes before and after it? A frame that cannot answer this is either unnecessary or evidence of a missing flow.

A workable inventory format looks like this:

Frame name Flow / task Entry point (from) Exit points (to) Priority Owner Status
01-Home Book a class Prototype start 02-Class List, 07-Profile P1 — core Amina Done
02-Class List Book a class 01-Home 03-Class Detail, 01-Home P1 — core Amina Done
03-Class Detail Book a class 02-Class List 04-Confirm Booking, 02-Class List P1 — core Jonah In progress
04-Confirm Booking Book a class 03-Class Detail 05-Booking Success P1 — core Jonah Not started
05-Booking Success Book a class 04-Confirm Booking 01-Home, 07-Profile P1 — core Jonah Not started
06-Class Full (error) Book a class — edge case 03-Class Detail 02-Class List P3 — edge Unassigned Backlog
07-Profile Manage account 01-Home, 05-Booking Success 01-Home P2 — secondary Priya In progress

Notice that the exit points column doubles as a prototyping checklist. If a frame lists two exits, the finished file must contain two working connections from that frame. This single column prevents most dead-end problems before they occur.

Prioritisation matters because time runs out. The critical path — the shortest sequence of screens that lets an evaluator complete the headline task from start to finish — must be built and connected first. A prototype with five polished core screens and a complete loop is far more persuasive than fifteen half-connected screens including three error states. Label screens P1 (core journey), P2 (secondary flows a user might reasonably take, such as viewing a profile), and P3 (edge cases: empty states, error messages, offline states). Build strictly in that order. If the deadline arrives with P3 untouched, the prototype still demonstrates a complete user journey.

Before anyone opens Figma, the team must agree a definition of done for a screen. "Done" is not "it looks finished to me." A usable definition is explicit and checkable:

  • Frame is sized to the agreed device preset (e.g. 390 × 844) and named using the agreed convention.
  • All repeating elements (buttons, nav bars, cards, input fields) are instances of shared library components — no detached or hand-drawn copies.
  • All colours come from published colour styles; all text uses published text styles. Zero ad-hoc hex values or one-off font sizes.
  • Layout uses auto-layout with the agreed spacing scale (e.g. 4/8/16/24) rather than manually nudged positions.
  • Copy is realistic and representative — no "Lorem ipsum", no "Button", no "Title goes here".
  • Every interactive element listed in the inventory's exit points has a working prototype connection with the agreed transition.
  • A back or cancel route exists wherever the user could reasonably want to retreat.

Write this list into the Figma file itself — a text frame on a "Team" page — so nobody has to go hunting for it. A screen is marked "Done" in the inventory only when its owner has checked it against every line.

Finally, the inventory is a living document. Review it at every team check-in: which screens moved to Done, which are blocked, which have slipped in priority. The purpose of the check-in is to surface blockers early — "I can't build the confirmation screen because we haven't decided what the card component looks like" is a five-minute problem on day two and a crisis on the day before submission.

Dividing Work Across Team Members

Figma's multiplayer editing is genuinely concurrent: two people can work in the same file at the same time and see each other's cursors. What it does not do is merge conflicting intentions. If two people independently restyle the same button, the last edit wins silently and the earlier work is simply gone. Division of labour is therefore about establishing exclusive ownership zones so that no two people ever have a legitimate reason to edit the same object.

The most reliable unit of ownership is the page, with the frame as a secondary unit. A sensible file structure for a four-person team:

📄 00 — Team (brief, screen inventory, definition of done, decisions log)
📄 01 — Design System (components, colour styles, text styles)  → Owner: Priya
📄 02 — Flow A: Booking                                          → Owner: Amina
📄 03 — Flow B: Account & Profile                                → Owner: Jonah
📄 04 — Flow C: Search & Discovery                               → Owner: Dani
📄 05 — Archive (superseded explorations, do not link)

Note the single owner for the Design System page. This is the most important ownership rule in the whole file. Shared components are, by definition, edited by one person and inherited by everyone; if three people are changing master components simultaneously, the entire file becomes unstable. Treat component changes as requests: a team member who needs a new variant posts a Figma comment on the component ("Need a destructive/red variant of Button for the Cancel Booking screen") and the library owner builds it. This takes slightly longer than doing it yourself and saves hours of reconciliation.

The rule that all members use shared library components rather than ad-hoc elements is what makes parallel work converge rather than diverge. Consider the alternative: Amina draws a button as a rectangle with a text layer, 16px radius, #2B5CE6 fill. Jonah draws his own at 12px radius, #2B5DE8. On their own screens each looks fine. Side by side in the final prototype they look like two different products — and fixing it late means hand-editing dozens of elements. With a shared component, Priya changes the master once and every instance across all four pages updates instantly. The same logic applies to styles: a published colour style named Brand/Primary can be re-tuned globally; a pasted hex value cannot.

Practical conventions that prevent conflicts:

  • Never edit outside your page without a comment and an acknowledgement. If you spot a problem on someone else's screen, comment — do not fix.
  • Never detach an instance to make a local change. If the component does not support what you need, request a variant or a property. Detaching breaks the inheritance chain permanently and is one of the most common QA failures.
  • Name everything as you go. 01-Home, 02-Class List, not Frame 427. Prototype connections and the inventory both depend on recognisable names.
  • Use the Archive page rather than deleting explorations. Deleted work occasionally needs recovering; abandoned frames left floating next to live ones get accidentally linked into the prototype.

Merging is a scheduled activity, not an accident. A short sync at the end of each working session — fifteen minutes, everyone in the file together — is enough. The agenda is fixed: walk the critical path in presentation mode, update the inventory statuses, look for visual inconsistencies (mismatched spacing, two shades of grey, inconsistent corner radii), and agree who fixes what. Visual inconsistency is easiest to spot when screens from different owners are placed adjacent on the canvas, so part of the sync is simply dragging frames next to each other and looking.

Figma comments are the team's asynchronous channel. A comment pinned to a specific element carries context that a chat message cannot: the reader sees exactly what you mean. Use comments for questions ("Should this CTA say 'Book' or 'Reserve'? Brief uses both"), review requests ("@Priya ready for your check"), and flags ("this card is detached — I'll rebuild from the library"). Crucially, comments live in an overlay and do not alter layers, so they add no risk to the file structure — unlike the common anti-pattern of dropping red text notes directly onto the canvas, which then has to be found and deleted before submission. Resolve comments once actioned so the remaining pins represent genuine open work.

Self-Review and Design QA

Design QA is the team's own inspection pass before anyone outside sees the file. It is deliberately separate from designing: you are not asking "is this a good idea?" but "does this meet the standard we agreed?" Run it against a checklist, screen by screen, in a single focused sitting — and have someone QA a screen they did not build, because owners are blind to their own omissions.

The first and highest-value check is flow completeness. Open the prototype in presentation mode and attempt every path in the inventory's exit-point column. A frame is a dead end if the user arrives and finds no way forward and no way back. Dead ends are the single most damaging defect in a student prototype because they stop an evaluator mid-task and make the whole thing feel unfinished. Common sources:

  • Success and confirmation screens built last, with no onward link to home.
  • Modals and overlays that open but have no close interaction.
  • Back arrows drawn as icons but never connected ("Back" is an element, not a link, until you attach it).
  • Connections pointing at a frame that was later renamed, duplicated, or moved to Archive.
  • Tab bars where only the active tab is connected, so three of five tabs do nothing.

Figma's prototype view shows connection noodles on the canvas; a frame with arrows entering but none leaving is immediately visible as a terminal node. Use that visual scan as a first pass, then confirm by clicking through. A useful habit: run the flow while narrating the user's goal aloud. If you reach a point where you say "and then they... hmm", that is a dead end or an unclear affordance.

The second check is style consistency. Every fill, stroke, and text layer should be driven by a published style. In Figma's right-hand panel, a styled property shows the style name; an ad-hoc value shows a raw hex or a loose font setting. Ad-hoc values creep in through copy-paste from older explorations, from images sampled with the eyedropper, and from text pasted with source formatting. Scan for them systematically — selecting all text layers on a frame and checking whether the type panel shows "Mixed" with no style name is a fast tell. The symptom to look for visually is near-duplicates: two greys that differ by a few percent, body text at 15px on one screen and 16px on another, 8px radius here and 10px there. None of these is noticeable alone; together they read as carelessness.

Third, confirm component integrity. Every repeated element should be an instance, not a detached copy. In the layers panel, instances carry the diamond icon; a detached copy appears as an ordinary frame or group. Detachment typically happens when someone needed to change something the component did not expose — so a detached instance is also a signal that your component needs an extra property or variant. Rebuild from the library and extend the component rather than leaving the local copy; otherwise a late change to the master silently misses that screen.

Fourth, replace placeholder content with realistic, representative copy. "Lorem ipsum dolor sit amet" tells an evaluator nothing and actively hides problems: real content has different lengths, and a card that looks balanced with placeholder text may break with a genuine 48-character class title. Realistic copy means plausible names, prices, dates, times, labels and error messages — "Vinyasa Flow · Tue 18:30 · 4 places left", not "Item name · Subtitle". Deliberately include at least one long value and one short value in any list so the layout is stress-tested. The same applies to images: grey boxes with an X are fine in a wireframe and conspicuous in a submitted high-fidelity prototype.

A compact QA checklist the team can paste into the file:

Dimension Check Pass criterion
Flow Every inventory exit point is a working connection No frame without an onward or return path
Flow Overlays and modals can be dismissed Close/cancel interaction present on each
Styles Fills and text use published styles No raw hex values or unstyled type
Components Repeated UI elements are library instances No detached copies in the layers panel
Layout Spacing follows the agreed scale Auto-layout used; padding values consistent
Content Copy is realistic and representative No lorem ipsum, no "Button", real data shapes
Hygiene File is clean for an external viewer Frames named, Archive page excluded from flow

Setting Up for Peer Evaluation

A prototype that is excellent internally can still fail the handover. Preparation for peer evaluation is about removing every obstacle between the evaluator and the user journey.

Begin with the start frame. Figma plays a prototype from the frame flagged with the flow start point; if the team never set one, Figma may begin from whichever frame was most recently selected or the first in the flow list, which can drop an evaluator into the middle of a checkout sequence with no context. Set the start deliberately to the most logical entry point — usually a splash, login, or home screen, matching what a first-time user would actually see. In Figma this is done by selecting the frame and adding a flow starting point in the Prototype panel; name the flow meaningfully ("Flow 1 — Book a class") because that name appears to the viewer. If the project demonstrates more than one task, create one named flow per task so evaluators can jump to each.

Next, set share permissions. Evaluators need can comment access, not can view and certainly not can edit. View-only prevents them from recording observations in place; edit access lets an outsider move your layers and invalidate your submission. Share link settings should typically be "Anyone with the link → can comment", unless the module requires restricting to the organisation. Copy the prototype link (from presentation view) rather than the file link, so evaluators land in the interactive player rather than the editor canvas — though note that comments can be left in both; pinned prototype comments attach to the frame being viewed, which is exactly what you want.

Supply a short context note. An evaluator with no briefing will comment on the wrong things — critiquing a deliberately out-of-scope screen, or missing the fact that only one of three flows is implemented. Four or five sentences is enough, placed in the Figma file description, on the Team page, or in the message accompanying the link:

Project: ClassPass-style class booking app (mobile, 390×844)
Audience: busy urban professionals booking fitness classes
Implemented flows: (1) Book a class — complete; (2) Cancel a booking — complete
Not implemented: payment entry, account creation (out of scope for this iteration)
Start here: tap "Browse classes" on the Home screen
We'd especially like feedback on: clarity of the confirmation step and
whether the bottom navigation labels are understandable.

That last line is disproportionately valuable: directed feedback is better feedback.

Finally, test the link as an outsider. Open an incognito or private browser window — or a different browser entirely — paste the link, and attempt the whole journey while signed out of your Figma account. This is the only reliable way to verify what an external evaluator will experience. The failures this catches are routine and embarrassing: the link is restricted to team members only; the link points at the file rather than the prototype; the start frame is wrong; a font used in the design is installed locally on your machine but renders as a fallback for everyone else; or the prototype opens at a zoom setting that crops the frame. Fix each, then test again. Make this a step in the definition of done for the submission itself, not an afterthought.

Conducting and Receiving Peer Evaluation

Peer evaluation produces useful results only when it is structured. Unstructured feedback gravitates to colour preferences and personal taste; structured feedback tests whether the prototype does its job.

The mechanism should be pinned Figma comments. A comment attached to a specific element on a specific frame is precise and actionable: the recipient sees exactly which button, which label, which spacing is being discussed. Compare two versions of the same observation:

  • General note: "Navigation was a bit confusing in places." — Unactionable. Which place? Which element? What was expected?
  • Pinned comment on 03-Class Detail, on the chevron icon: "I expected this arrow to take me back to the class list, but nothing happened. I then tried the logo at the top, which also did nothing — I had to restart the prototype." — Immediately fixable, and it names the behaviour the user expected.

Good comments describe observation, expectation, and consequence: what you did, what you thought would happen, what actually happened. Avoid prescribing a solution as the whole comment ("make this button blue") because it hides the underlying problem; state the problem and then, if you wish, offer the suggestion as a second sentence.

Evaluators should actively hunt for three categories of defect:

  • Dead ends — points where the journey stops. Record the frame name and what you tried.
  • Unclear affordances — elements that do not communicate whether they are interactive. A card with no visual cue that it is tappable; a label that looks like a button; an icon with no recognised meaning; a disabled-looking control that is actually active. Affordance failures often show up as hesitation: note anywhere you paused and had to guess.
  • Expectation mismatches — the interaction works but surprises you. A "Save" that navigates away; a modal that appears as a full page; a back gesture that returns to the wrong screen; a success state with no confirmation of what was booked.

Evaluate flow completeness and visual design quality as separate dimensions. They are genuinely independent — a beautiful prototype can be unnavigable, and a plain one can be flawlessly connected — and conflating them produces muddled scores and muddled fixes. A simple two-dimension rubric keeps them apart:

Dimension What is being judged Evidence to cite Typical failure
Flow completeness Can the stated task be completed end to end without restarting? Frame names where the journey stalled; number of dead ends found; whether back/cancel routes exist Confirmation screen with no route home; two of five tab bar items inert
Interaction quality Do transitions, overlays and states behave as a real app would? Transitions that contradict direction of travel; modals that cannot be dismissed; missing hover/pressed states Every link set to "Instant" so the user cannot tell whether anything happened
Visual hierarchy Is the primary action on each screen obvious within a few seconds? Where your eye landed first; whether the main CTA competes with secondary buttons Three equally weighted buttons; headline and body at near-identical size
Consistency Do equivalent elements look and behave the same across screens? Screens where spacing, type size, radius or colour drift Nav bar 8px taller on two screens built by a different team member
Affordance and clarity Is it obvious what is interactive and what each control does? Elements you hesitated over or tapped by mistake Unlabelled icon-only actions; cards with no tap cue
Content realism Does the copy support plausible evaluation of the design? Placeholder strings; data that would never occur in reality "Lorem ipsum" in a card that must hold a 50-character title

Scoring each dimension separately (for example 1–5, with a one-line justification) forces evaluators to notice that "I didn't like it" usually resolves into one specific dimension — and it tells the receiving team where to spend their remaining time.

Every evaluation must close with at least two constructive suggestions alongside the issues raised. A suggestion is constructive when it is specific, achievable within the remaining time, and tied to an observed problem rather than to taste. Compare:

  • Not constructive: "The home screen is boring." — Taste, no observation, no action.
  • Constructive: "On 01-Home the 'Browse classes' and 'My bookings' buttons have identical weight, and I wasn't sure which was the main action. Consider making 'Browse classes' the filled primary button and 'My bookings' a text or outline button, so the primary task is obvious on arrival."
  • Constructive: "The booking confirmation uses an Instant transition, so it felt like nothing happened. A 'Move in' transition from the right, matching the forward direction of the flow, would make the progression readable."

On the receiving side, there is a discipline too. Do not defend the design in the comment thread during the evaluation session; the evaluator's confusion is data, and explaining it away destroys the data. Reply only to clarify facts ("that screen is deliberately out of scope — noted in the context note") and otherwise acknowledge and record. Resist the urge to fix things live while evaluation is running, because the evaluator's remaining comments will then refer to a file that has already changed. Collect first, act afterwards.

Iterating Based on Feedback

Feedback is only valuable once it has been triaged. A group typically receives twenty to forty comments and has limited time; treating them as an undifferentiated queue means the team spends an hour adjusting a shadow while a broken link remains broken. Sort every comment into severity bands before touching the file:

Band Definition Examples Action
Critical — blocking Prevents an evaluator from completing the stated task Dead-end frame; modal with no close; wrong or missing prototype start frame; link permissions wrong Fix immediately, before anything else
Major — comprehension Task is completable but the user is confused or misled Unclear icon-only action; primary CTA not distinguishable; misleading transition direction; placeholder copy on a core screen Fix after all critical items
Minor — polish Cosmetic inconsistency that does not impede use 4px spacing drift; two near-identical greys; inconsistent corner radius; icon optical alignment Fix if time allows; batch by style or component
Out of scope / won't fix Valid but outside the brief or this iteration "Add dark mode"; "build the payment flow"; conflicting taste preferences Record with a one-line rationale; do not silently ignore

The sequencing rule is non-negotiable: repair broken prototype connections before any visual refinement. There are two reasons. First, a navigable but plain prototype demonstrates the skill being assessed — simulating realistic user interaction — whereas a beautiful dead end demonstrates nothing. Second, visual refinement can itself break connections: replacing a hand-drawn button with a component instance, or restructuring a frame into auto-layout, detaches or relocates the hotspot the connection was attached to. Fix flow, verify flow, then style, then verify flow again.

Work through the critical band in one pass with a single person driving while the inventory's exit-point column is open beside them, because that column is the definitive list of connections that must exist. Then re-run the full critical path in presentation mode. Only when the path is clean should the team move to major and minor items, assigning them back to the owner of the relevant page so that ownership discipline survives the revision phase. Minor cosmetic issues are usually best fixed at the component or style level rather than screen by screen: if the grey is wrong, correct the published colour style once and every instance follows.

Throughout, document what changed and why. A change log serves three purposes: it demonstrates to evaluators that their feedback was taken seriously, it prevents the same issue being raised twice, and it supplies the evidence base for the reflective component that most academic submissions require. Keep it in the Figma file on the Team page, or in the submission document, in a simple tabular form:

# Feedback received (source) Severity Decision and change made Owner Status
1 "Back chevron on 03-Class Detail does nothing" (Group B, pinned comment) Critical Connected chevron to 02-Class List with "Move out" transition; audited all other back icons and connected four more Jonah Done — comment resolved
2 "Couldn't tell which button was the main action on Home" (Group B) Major Applied Button/Primary variant to "Browse classes", Button/Secondary to "My bookings"; updated component variant list Priya Done
3 "Success screen uses lorem ipsum" (Group B) Major Replaced with real booking summary copy including class name, time and studio address Amina Done
4 "Card shadows inconsistent between flows" (self-QA) Minor Created shared effect style Elevation/Card and applied to the Card master component Priya Done
5 "Add a dark mode" (Group B) Out of scope Noted as a future iteration; not required by the brief and not achievable in remaining time Team Deferred — rationale recorded

Deciding not to act is a legitimate outcome, provided the rationale is written down. Evaluators are not always right: a comment may reflect an unfamiliarity with the platform's conventions, or may conflict with another evaluator's comment. Record the conflict and the reasoning ("Group B wanted the filter above the list, Group C below; retained above to match iOS convention and the pattern used on 02"). This is exactly the kind of justified design judgement that assessment rubrics reward.

Close the loop properly. Once revisions are complete, resolve each addressed comment in Figma — ideally with a one-line reply saying what was done — then run the incognito link test again, because permissions and start frames can be disturbed by file reorganisation. Finally, re-share the updated link and notify the evaluators that a revised version is available, pointing them to the change log and, if useful, to the specific flows you would like them to re-check. Re-notification matters: an evaluator who is never told their comment was actioned has no way to validate the fix, and a second quick pass often catches a change that solved one problem while creating another. For submission, hand in the prototype link with comment access enabled, confirm the named flows and start frame are correct, and attach the screen inventory and change log as evidence of process — the artefacts that show not only what the team built, but how it was built, verified and improved.
