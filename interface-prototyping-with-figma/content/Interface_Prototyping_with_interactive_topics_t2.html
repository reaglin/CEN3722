Frames, Grids, and Screen Layout

▶

Every digital interface — whether a mobile app, a web dashboard, or a tablet experience — needs a structured container to hold its content. In Figma, that container is called a frame. Frames are the single most important structural element in Figma's design system. Unlike simple rectangles or groups, frames carry a unique set of properties that make them the right choice for representing screens, components, and layout regions. Understanding how frames work, how to apply layout grids inside them, how to anchor elements responsively with constraints, and how to organise multiple screens into coherent flows will give you full control over professional-quality interface design. This topic covers each of those areas in depth.

A frame in Figma is a special type of container node. You create one by pressing F on the keyboard and drawing on the canvas, or by selecting a preset from the right-hand properties panel. On the surface a frame looks like a rectangle, but its behaviour is fundamentally different. Frames establish their own coordinate system: every child element placed inside a frame measures its position relative to the frame's top-left corner, not relative to the canvas. This makes frames the correct building block for anything that represents a real screen, a component boundary, or a layout region.

Fixed dimensions and device presets are one of the first things you will configure when creating a frame. Rather than guessing pixel dimensions, Figma ships with a library of presets that match the exact viewport sizes used by real devices and browsers. When you draw a frame and look at the right panel, you will see a dropdown containing categories such as Phone, Tablet, Desktop, Watch, Paper, and Social Media. Choosing iPhone 14 Pro, for example, instantly resizes your frame to 393 × 852 pixels — the logical resolution Apple uses for that device. Choosing Desktop gives you a standard 1440 × 1024 canvas. Using these presets from the start means your design will map predictably to the real device when you hand off specs to a developer or run a prototype.

Frames clip their contents by default. This is a critical behaviour to understand early. When an element — say, an image or an overflowing text block — extends beyond the frame boundary, Figma hides the parts that fall outside. The visual result is exactly what a real screen shows: content that exceeds the viewport is not visible until the user scrolls. You can toggle clipping on or off using the Clip content checkbox in the frame's design properties, but for screen-level frames you should generally leave it enabled so your designs accurately represent what a user will actually see.

Nested frames are where Figma's power really shows. A frame can contain other frames inside it, and those inner frames can contain more frames still. This nesting is the foundation for building components: a Button component is a frame containing a text layer and perhaps an icon frame; a Card component is a frame containing an image frame, a text frame, and a button frame. Auto-layout containers — which you will explore in a later module — are themselves frames with special layout rules applied. Thinking in nested frames rather than flat layers leads to designs that are easier to maintain, easier to hand off, and far easier to turn into interactive prototypes.

One of the most practical distinctions in Figma is that frames appear as distinct nodes in a prototype flow, whereas groups do not. When you add a prototype connection, Figma lets you navigate to a frame. You cannot navigate to a group. This means that every screen in your prototype must be a top-level frame, and every component that needs its own scroll behaviour or overlay behaviour must also be a frame. Groups are useful for moving several layers together on the canvas, but they carry no screen-level meaning. Forming the habit of using frames — not groups — for anything structural will save you hours of rework when you begin prototyping.

Once you have a frame representing a screen, the next step is to impose order on its contents using a layout grid. A layout grid is a visual overlay that divides the frame into regions, giving you consistent reference lines for placing elements. Grids do not affect the actual position of your layers — they are guides, not containers — but designing to a grid produces interfaces that feel balanced, professional, and consistent across screens.

The most common grid type in UI design is the column grid. A column grid divides the frame horizontally into a fixed number of equal-width columns separated by gutters. Mobile designs traditionally use 4 columns; tablet designs use 8; desktop designs use 12. To add a column grid in Figma, click the + icon next to Layout grid in the design panel, then change the grid type from Grid to Columns. You can then set the count, gutter width, margin, and whether the columns have a fixed width or stretch to fill available space.

Gutters and margins are the two spacing controls that make a column grid usable. The margin is the space between the left or right edge of the frame and the first or last column — it defines the "safe zone" where content sits away from the screen edge. The gutter is the gap between adjacent columns. A common mobile configuration is 16 px margins and 16 px gutters with 4 columns; a common desktop configuration is 24 px margins and 24 px gutters with 12 columns. These numbers are conventions, not laws — your design system may specify different values — but consistency within a project is what matters most.

Figma allows you to stack multiple grids on a single frame. This is useful for complex layouts that need both column guidance and row guidance simultaneously. A data dashboard, for example, might carry a 12-column grid for horizontal alignment plus a row grid set to an 8 px baseline for consistent vertical rhythm. You could also stack two column grids with different colours: one representing the outer container grid and another representing a nested content grid. Each grid in the stack can be toggled on and off independently using the eye icon beside it.

It is important to remember that grids are visible only in the editor. When you export a frame as a PNG or PDF, or when a stakeholder views your prototype in a browser, the grid overlay does not appear. This is intentional — grids are a design tool, not a visual element of the interface itself. The keyboard shortcut Ctrl + Shift + 4 (Windows) or Cmd + Shift + 4 (Mac) toggles grid visibility so you can quickly check alignment without permanently showing or hiding your grids.

With a frame sized correctly and a grid providing structure, the next challenge is making sure individual elements stay in the right position as the frame size changes. That is the job of constraints. A constraint tells Figma how a child element should behave relative to its parent frame when the parent is resized. This is what makes designs responsive: rather than every element shifting randomly when you change a frame's width, constraints anchor elements exactly where you intend them to be.

Horizontal constraints can be set to one of five values for each element. Left keeps the element a fixed distance from the left edge of the frame — the default behaviour, appropriate for most content that should stay left-aligned. Right keeps the element a fixed distance from the right edge, useful for floating action buttons or icons that live on the right side of a header. Left and Right stretches the element so that both its left and right edges maintain fixed distances from the frame's edges — useful for full-width bars like navigation bars and footers that should always span the entire width. Center keeps the element horizontally centred in the frame regardless of width — useful for logos or hero text. Scale scales the element proportionally as the frame grows or shrinks, behaving like a percentage-based width.

Vertical constraints offer an identical set of options applied to the vertical axis: Top, Bottom, Top and Bottom, Center, and Scale. The Top and Bottom option is particularly useful for elements that must stretch vertically — a sidebar that should always fill the full height of the screen regardless of viewport height, for example.

A classic practical use of constraints is pinning a navigation bar to the top of a screen. To achieve this, set the nav bar's horizontal constraint to Left and Right (so it always spans the full width) and its vertical constraint to Top (so it always sits exactly at the top of the frame). Now, if you resize the frame from 375 px wide (mobile) to 768 px wide (tablet), the nav bar expands to fill the new width and remains pinned at the top. Similarly, a tab bar at the bottom of a mobile screen should use Left and Right horizontally and Bottom vertically.

One important rule to keep in mind: constraints are superseded by auto-layout rules when both are applied to the same element. If a child element lives inside an auto-layout frame, the auto-layout's axis rules control how that element is sized and positioned along the layout direction. Constraints still apply to the element's behaviour on the axis that auto-layout does not control, but on the primary axis auto-layout wins. This is a common source of confusion for new Figma users. The safest mental model is: use constraints for screen-level frames and manually positioned elements; use auto-layout for components and repeating patterns.

Designing for real devices requires more than just getting the pixel dimensions right. You also need to account for safe areas — the regions of a mobile screen that the operating system reserves for its own system UI. On an iPhone with a dynamic island, the top safe area extends roughly 59 pt below the top edge to clear the dynamic island. On most iPhones, the bottom safe area extends roughly 34 pt above the home indicator. Content — especially interactive elements like buttons, links, and form fields — should not be placed inside these regions, because users may find them partially obscured or difficult to tap.

Android devices have analogous concepts: the status bar at the top (24 dp tall) and the navigation bar or gesture area at the bottom. The exact measurements vary by manufacturer and OS version, which is why many design systems define a safe area component that can be placed on every screen frame as a reference layer, showing the designer exactly where content should and should not go.

For presentations to stakeholders or during peer design reviews, wrapping your frames in a device mockup significantly improves realism and comprehension. A device frame plugin — such as Mockup or Clay Mockups 3D — places your design inside a photorealistic phone or laptop shell. Alternatively, you can import a flat mockup SVG and use the fill settings to embed your frame's content. When your audience sees the design inside a recognisable device, they find it easier to evaluate proportions, spacing, and readability.

An important resolution consideration: design at 1× and export at 2× or 3×. In Figma, one point corresponds to one pixel at 1× scale. A modern iPhone has a pixel ratio of 3×, meaning each logical point is rendered using a 3×3 grid of physical pixels. If you design a 44 pt button at 1× and export at 3×, Figma outputs a 132 px × 132 px image — perfectly sharp on a Retina or Super Retina display. If you had originally designed at 3× and placed your elements at triple sizes, your spacing numbers would be inflated and harder to reason about. Designing at 1× keeps numbers human-readable while the export settings handle density.

As a project grows, a single Figma file can contain dozens or even hundreds of frames spread across the canvas. Without deliberate organisation, this becomes chaotic. The solution is to group frames into flows — each flow representing one coherent user journey through the product. A typical mobile application might have flows for Onboarding, Login and Authentication, Home Feed, Product Detail, Checkout, Order Confirmation, and Settings. Each flow contains the sequence of screens a user would encounter during that journey, and each flow lives in its own horizontal or vertical band of the canvas.

A starting frame is the first frame in a flow. In Figma's prototype panel, you designate starting frames explicitly by clicking Add starting point when a frame is selected. The starting frame becomes the entry point when you present or preview that flow. Multiple starting frames can exist in a single file — one per flow — so that you can demo the checkout flow independently from the onboarding flow without having to navigate through every screen.

Naming frames sequentially is a small habit that produces large organisational benefits. A sequence like Onboarding-01, Onboarding-02, Onboarding-03 immediately communicates screen order to any collaborator who opens the file. When frames are named generically — Frame 1, Frame 47 — developers and product managers have no way to understand intent without opening every frame individually. Consistent naming also makes Figma's search panel (Ctrl/Cmd + F) useful: searching for Checkout instantly filters to only the checkout screens.

Colour-coded frame backgrounds are another organisational technique that pays dividends during design reviews. Assigning a unique background colour to each flow — say, light blue for Onboarding, warm yellow for Checkout, light green for Settings — lets anyone viewing the canvas instantly understand which flow a given screen belongs to, even before reading its name. This is especially useful during group critique sessions where you zoom out to see the full canvas and discuss which parts of the experience are complete, in progress, or not yet started.

To put these concepts together, consider a practical example. You are designing the onboarding flow for a fitness application. You create a top-level frame using the iPhone 14 Pro preset (393 × 852 px). Inside that frame you add a 4-column layout grid with 16 px margins and 16 px gutters to guide your content placement. You nest a header frame constrained to Left and Right horizontally and Top vertically so it always sits flush against the top. Inside the header you place a logo constrained to Center horizontally so it stays centred regardless of future frame width adjustments. At the bottom of the screen you nest a primary button frame constrained to Left and Right and Bottom, placing it above the safe area boundary. You name this frame Onboarding-01 and duplicate it three times to create Onboarding-02, Onboarding-03, and Onboarding-04. You mark Onboarding-01 as the starting frame in the prototype panel and give all four frames a light blue background to distinguish them from the login flow screens that sit in the next row of the canvas. The result is a well-structured, self-documenting design file that is ready for prototyping, handoff, and collaborative review.
