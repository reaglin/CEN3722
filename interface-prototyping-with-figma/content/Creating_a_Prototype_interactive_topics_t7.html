Building and Submitting the Group Project Prototype

▶

The final stage of a prototyping module is where every isolated skill — frames, components, auto-layout, styles, and interactive connections — stops being an exercise and becomes a deliverable. Building a group project prototype is as much a coordination problem as a design problem. A single designer working alone can tolerate an untidy file because they hold the structure in their head; a team of four cannot. The moment three people are editing the same Figma file, the cost of an undocumented decision, a detached component, or an unassigned screen multiplies. This topic walks through a complete delivery process: defining what must be built, dividing it safely, checking it against an agreed standard, preparing it for outside eyes, running a structured peer evaluation, and closing the loop with documented iteration.

The underlying discipline is simple to state and hard to practise: decide before you build, build to the decision, and verify against the decision. Most group prototypes that fail at submission do not fail because the visual design is poor. They fail because two people built the same screen differently, a flow dead-ends halfway through checkout, or the shared link opens on an arbitrary frame in the middle of the file. Each section below targets one of those failure modes.

Project Scope and Screen Inventory

A screen inventory is a written list of every frame the prototype requires, with each frame tied explicitly to a user task. It is the contract between the team and the brief. Without it, scope expands silently — someone adds a "settings" screen nobody asked for while the core booking flow is still missing two steps.

The inventory should be built from flows, not from a wishlist of pages. Start by writing the user tasks the prototype must demonstrate ("a user signs in and books a class", "a user cancels an existing booking"), then decompose each task into the screens required to complete it. Every frame in the inventory must answer the question: which task does this serve, and what comes before and after it? A frame that cannot answer this is either unnecessary or evidence of a missing flow.

A workable inventory format looks like this:

Frame name Flow / task Entry point (from) Exit points (to) Priority Owner Status
01-Home Book a class Prototype start 02-Class List, 07-Profile P1 — core Amina Done
02-Class List Book a class 01-Home 03-Class Detail, 01-Home P1 — core Amina Done
03-Class Detail Book a class 02-Class List 04-Confirm Booking, 02-Class List P1 — core Jonah In progress
04-Confirm Booking Book a class 03-Class Detail 05-Booking Success P1 — core Jonah Not started
05-Booking Success Book a class 04-Confirm Booking 01-Home, 07-Profile P1 — core Jonah Not started
06-Class Full (error) Book a class — edge case 03-Class Detail 02-Class List P3 — edge Unassigned Backlog
07-Profile Manage account 01-Home, 05-Booking Success 01-Home P2 — secondary Priya In progress

Notice that the exit points column doubles as a prototyping checklist. If a frame lists two exits, the finished file must contain two working connections from that frame. This single column prevents most dead-end problems before they occur.

Prioritisation matters because time runs out. The critical path — the shortest sequence of screens that lets an evaluator complete the headline task from start to finish — must be built and connected first. A prototype with five polished core screens and a complete loop is far more persuasive than fifteen half-connected screens including three error states. Label screens P1 (core journey), P2 (secondary flows a user might reasonably take, such as viewing a profile), and P3 (edge cases: empty states, error messages, offline states). Build strictly in that order. If the deadline arrives with P3 untouched, the prototype still demonstrates a complete user journey.

Before anyone opens Figma, the team must agree a definition of done for a screen. "Done" is not "it looks finished to me." A usable definition is explicit and checkable:

  • Frame is sized to the agreed device preset (e.g. 390 × 844) and named using the agreed convention.
  • All repeating elements (buttons, nav bars, cards, input fields) are instances of shared library components — no detached or hand-drawn copies.
  • All colours come from published colour styles; all text uses published text styles. Zero ad-hoc hex values or one-off font sizes.
  • Layout uses auto-layout with the agreed spacing scale (e.g. 4/8/16/24) rather than manually nudged positions.
  • Copy is realistic and representative — no "Lorem ipsum", no "Button", no "Title goes here".
  • Every interactive element listed in the inventory's exit points has a working prototype connection with the agreed transition.
  • A back or cancel route exists wherever the user could reasonably want to retreat.

Write this list into the Figma file itself — a text frame on a "Team" page — so nobody has to go hunting for it. A screen is marked "Done" in the inventory only when its owner has checked it against every line.

Finally, the inventory is a living document. Review it at every team check-in: which screens moved to Done, which are blocked, which have slipped in priority. The purpose of the check-in is to surface blockers early — "I can't build the confirmation screen because we haven't decided what the card component looks like" is a five-minute problem on day two and a crisis on the day before submission.

Dividing Work Across Team Members

Figma's multiplayer editing is genuinely concurrent: two people can work in the same file at the same time and see each other's cursors. What it does not do is merge conflicting intentions. If two people independently restyle the same button, the last edit wins silently and the earlier work is simply gone. Division of labour is therefore about establishing exclusive ownership zones so that no two people ever have a legitimate reason to edit the same object.

The most reliable unit of ownership is the page, with the frame as a secondary unit. A sensible file structure for a four-person team:

📄 00 — Team (brief, screen inventory, definition of done, decisions log)
📄 01 — Design System (components, colour styles, text styles)  → Owner: Priya
📄 02 — Flow A: Booking                                          → Owner: Amina
📄 03 — Flow B: Account & Profile                                → Owner: Jonah
📄 04 — Flow C: Search & Discovery                               → Owner: Dani
📄 05 — Archive (superseded explorations, do not link)

Note the single owner for the Design System page. This is the most important ownership rule in the whole file. Shared components are, by definition, edited by one person and inherited by everyone; if three people are changing master components simultaneously, the entire file becomes unstable. Treat component changes as requests: a team member who needs a new variant posts a Figma comment on the component ("Need a destructive/red variant of Button for the Cancel Booking screen") and the library owner builds it. This takes slightly longer than doing it yourself and saves hours of reconciliation.

The rule that all members use shared library components rather than ad-hoc elements is what makes parallel work converge rather than diverge. Consider the alternative: Amina draws a button as a rectangle with a text layer, 16px radius, #2B5CE6 fill. Jonah draws his own at 12px radius, #2B5DE8. On their own screens each looks fine. Side by side in the final prototype they look like two different products — and fixing it late means hand-editing dozens of elements. With a shared component, Priya changes the master once and every instance across all four pages updates instantly. The same logic applies to styles: a published colour style named Brand/Primary can be re-tuned globally; a pasted hex value cannot.

Practical conventions that prevent conflicts:

  • Never edit outside your page without a comment and an acknowledgement. If you spot a problem on someone else's screen, comment — do not fix.
  • Never detach an instance to make a local change. If the component does not support what you need, request a variant or a property. Detaching breaks the inheritance chain permanently and is one of the most common QA failures.
  • Name everything as you go. 01-Home, 02-Class List, not Frame 427. Prototype connections and the inventory both depend on recognisable names.
  • Use the Archive page rather than deleting explorations. Deleted work occasionally needs recovering; abandoned frames left floating next to live ones get accidentally linked into the prototype.

Merging is a scheduled activity, not an accident. A short sync at the end of each working session — fifteen minutes, everyone in the file together — is enough. The agenda is fixed: walk the critical path in presentation mode, update the inventory statuses, look for visual inconsistencies (mismatched spacing, two shades of grey, inconsistent corner radii), and agree who fixes what. Visual inconsistency is easiest to spot when screens from different owners are placed adjacent on the canvas, so part of the sync is simply dragging frames next to each other and looking.

Figma comments are the team's asynchronous channel. A comment pinned to a specific element carries context that a chat message cannot: the reader sees exactly what you mean. Use comments for questions ("Should this CTA say 'Book' or 'Reserve'? Brief uses both"), review requests ("@Priya ready for your check"), and flags ("this card is detached — I'll rebuild from the library"). Crucially, comments live in an overlay and do not alter layers, so they add no risk to the file structure — unlike the common anti-pattern of dropping red text notes directly onto the canvas, which then has to be found and deleted before submission. Resolve comments once actioned so the remaining pins represent genuine open work.

Self-Review and Design QA

Design QA is the team's own inspection pass before anyone outside sees the file. It is deliberately separate from designing: you are not asking "is this a good idea?" but "does this meet the standard we agreed?" Run it against a checklist, screen by screen, in a single focused sitting — and have someone QA a screen they did not build, because owners are blind to their own omissions.

The first and highest-value check is flow completeness. Open the prototype in presentation mode and attempt every path in the inventory's exit-point column. A frame is a dead end if the user arrives and finds no way forward and no way back. Dead ends are the single most damaging defect in a student prototype because they stop an evaluator mid-task and make the whole thing feel unfinished. Common sources:

  • Success and confirmation screens built last, with no onward link to home.
  • Modals and overlays that open but have no close interaction.
  • Back arrows drawn as icons but never connected ("Back" is an element, not a link, until you attach it).
  • Connections pointing at a frame that was later renamed, duplicated, or moved to Archive.
  • Tab bars where only the active tab is connected, so three of five tabs do nothing.

Figma's prototype view shows connection noodles on the canvas; a frame with arrows entering but none leaving is immediately visible as a terminal node. Use that visual scan as a first pass, then confirm by clicking through. A useful habit: run the flow while narrating the user's goal aloud. If you reach a point where you say "and then they... hmm", that is a dead end or an unclear affordance.

The second check is style consistency. Every fill, stroke, and text layer should be driven by a published style. In Figma's right-hand panel, a styled property shows the style name; an ad-hoc value shows a raw hex or a loose font setting. Ad-hoc values creep in through copy-paste from older explorations, from images sampled with the eyedropper, and from text pasted with source formatting. Scan for them systematically — selecting all text layers on a frame and checking whether the type panel shows "Mixed" with no style name is a fast tell. The symptom to look for visually is near-duplicates: two greys that differ by a few percent, body text at 15px on one screen and 16px on another, 8px radius here and 10px there. None of these is noticeable alone; together they read as carelessness.

Third, confirm component integrity. Every repeated element should be an instance, not a detached copy. In the layers panel, instances carry the diamond icon; a detached copy appears as an ordinary frame or group. Detachment typically happens when someone needed to change something the component did not expose — so a detached instance is also a signal that your component needs an extra property or variant. Rebuild from the library and extend the component rather than leaving the local copy; otherwise a late change to the master silently misses that screen.

Fourth, replace placeholder content with realistic, representative copy. "Lorem ipsum dolor sit amet" tells an evaluator nothing and actively hides problems: real content has different lengths, and a card that looks balanced with placeholder text may break with a genuine 48-character class title. Realistic copy means plausible names, prices, dates, times, labels and error messages — "Vinyasa Flow · Tue 18:30 · 4 places left", not "Item name · Subtitle". Deliberately include at least one long value and one short value in any list so the layout is stress-tested. The same applies to images: grey boxes with an X are fine in a wireframe and conspicuous in a submitted high-fidelity prototype.

A compact QA checklist the team can paste into the file:

Dimension Check Pass criterion
Flow Every inventory exit point is a working connection No frame without an onward or return path
Flow Overlays and modals can be dismissed Close/cancel interaction present on each
Styles Fills and text use published styles No raw hex values or unstyled type
Components Repeated UI elements are library instances No detached copies in the layers panel
Layout Spacing follows the agreed scale Auto-layout used; padding values consistent
Content Copy is realistic and representative No lorem ipsum, no "Button", real data shapes
Hygiene File is clean for an external viewer Frames named, Archive page excluded from flow

Setting Up for Peer Evaluation

A prototype that is excellent internally can still fail the handover. Preparation for peer evaluation is about removing every obstacle between the evaluator and the user journey.

Begin with the start frame. Figma plays a prototype from the frame flagged with the flow start point; if the team never set one, Figma may begin from whichever frame was most recently selected or the first in the flow list, which can drop an evaluator into the middle of a checkout sequence with no context. Set the start deliberately to the most logical entry point — usually a splash, login, or home screen, matching what a first-time user would actually see. In Figma this is done by selecting the frame and adding a flow starting point in the Prototype panel; name the flow meaningfully ("Flow 1 — Book a class") because that name appears to the viewer. If the project demonstrates more than one task, create one named flow per task so evaluators can jump to each.

Next, set share permissions. Evaluators need can comment access, not can view and certainly not can edit. View-only prevents them from recording observations in place; edit access lets an outsider move your layers and invalidate your submission. Share link settings should typically be "Anyone with the link → can comment", unless the module requires restricting to the organisation. Copy the prototype link (from presentation view) rather than the file link, so evaluators land in the interactive player rather than the editor canvas — though note that comments can be left in both; pinned prototype comments attach to the frame being viewed, which is exactly what you want.

Supply a short context note. An evaluator with no briefing will comment on the wrong things — critiquing a deliberately out-of-scope screen, or missing the fact that only one of three flows is implemented. Four or five sentences is enough, placed in the Figma file description, on the Team page, or in the message accompanying the link:

Project: ClassPass-style class booking app (mobile, 390×844)
Audience: busy urban professionals booking fitness classes
Implemented flows: (1) Book a class — complete; (2) Cancel a booking — complete
Not implemented: payment entry, account creation (out of scope for this iteration)
Start here: tap "Browse classes" on the Home screen
We'd especially like feedback on: clarity of the confirmation step and
whether the bottom navigation labels are understandable.

That last line is disproportionately valuable: directed feedback is better feedback.

Finally, test the link as an outsider. Open an incognito or private browser window — or a different browser entirely — paste the link, and attempt the whole journey while signed out of your Figma account. This is the only reliable way to verify what an external evaluator will experience. The failures this catches are routine and embarrassing: the link is restricted to team members only; the link points at the file rather than the prototype; the start frame is wrong; a font used in the design is installed locally on your machine but renders as a fallback for everyone else; or the prototype opens at a zoom setting that crops the frame. Fix each, then test again. Make this a step in the definition of done for the submission itself, not an afterthought.

Conducting and Receiving Peer Evaluation

Peer evaluation produces useful results only when it is structured. Unstructured feedback gravitates to colour preferences and personal taste; structured feedback tests whether the prototype does its job.

The mechanism should be pinned Figma comments. A comment attached to a specific element on a specific frame is precise and actionable: the recipient sees exactly which button, which label, which spacing is being discussed. Compare two versions of the same observation:

  • General note: "Navigation was a bit confusing in places." — Unactionable. Which place? Which element? What was expected?
  • Pinned comment on 03-Class Detail, on the chevron icon: "I expected this arrow to take me back to the class list, but nothing happened. I then tried the logo at the top, which also did nothing — I had to restart the prototype." — Immediately fixable, and it names the behaviour the user expected.

Good comments describe observation, expectation, and consequence: what you did, what you thought would happen, what actually happened. Avoid prescribing a solution as the whole comment ("make this button blue") because it hides the underlying problem; state the problem and then, if you wish, offer the suggestion as a second sentence.

Evaluators should actively hunt for three categories of defect:

  • Dead ends — points where the journey stops. Record the frame name and what you tried.
  • Unclear affordances — elements that do not communicate whether they are interactive. A card with no visual cue that it is tappable; a label that looks like a button; an icon with no recognised meaning; a disabled-looking control that is actually active. Affordance failures often show up as hesitation: note anywhere you paused and had to guess.
  • Expectation mismatches — the interaction works but surprises you. A "Save" that navigates away; a modal that appears as a full page; a back gesture that returns to the wrong screen; a success state with no confirmation of what was booked.

Evaluate flow completeness and visual design quality as separate dimensions. They are genuinely independent — a beautiful prototype can be unnavigable, and a plain one can be flawlessly connected — and conflating them produces muddled scores and muddled fixes. A simple two-dimension rubric keeps them apart:

Dimension What is being judged Evidence to cite Typical failure
Flow completeness Can the stated task be completed end to end without restarting? Frame names where the journey stalled; number of dead ends found; whether back/cancel routes exist Confirmation screen with no route home; two of five tab bar items inert
Interaction quality Do transitions, overlays and states behave as a real app would? Transitions that contradict direction of travel; modals that cannot be dismissed; missing hover/pressed states Every link set to "Instant" so the user cannot tell whether anything happened
Visual hierarchy Is the primary action on each screen obvious within a few seconds? Where your eye landed first; whether the main CTA competes with secondary buttons Three equally weighted buttons; headline and body at near-identical size
Consistency Do equivalent elements look and behave the same across screens? Screens where spacing, type size, radius or colour drift Nav bar 8px taller on two screens built by a different team member
Affordance and clarity Is it obvious what is interactive and what each control does? Elements you hesitated over or tapped by mistake Unlabelled icon-only actions; cards with no tap cue
Content realism Does the copy support plausible evaluation of the design? Placeholder strings; data that would never occur in reality "Lorem ipsum" in a card that must hold a 50-character title

Scoring each dimension separately (for example 1–5, with a one-line justification) forces evaluators to notice that "I didn't like it" usually resolves into one specific dimension — and it tells the receiving team where to spend their remaining time.

Every evaluation must close with at least two constructive suggestions alongside the issues raised. A suggestion is constructive when it is specific, achievable within the remaining time, and tied to an observed problem rather than to taste. Compare:

  • Not constructive: "The home screen is boring." — Taste, no observation, no action.
  • Constructive: "On 01-Home the 'Browse classes' and 'My bookings' buttons have identical weight, and I wasn't sure which was the main action. Consider making 'Browse classes' the filled primary button and 'My bookings' a text or outline button, so the primary task is obvious on arrival."
  • Constructive: "The booking confirmation uses an Instant transition, so it felt like nothing happened. A 'Move in' transition from the right, matching the forward direction of the flow, would make the progression readable."

On the receiving side, there is a discipline too. Do not defend the design in the comment thread during the evaluation session; the evaluator's confusion is data, and explaining it away destroys the data. Reply only to clarify facts ("that screen is deliberately out of scope — noted in the context note") and otherwise acknowledge and record. Resist the urge to fix things live while evaluation is running, because the evaluator's remaining comments will then refer to a file that has already changed. Collect first, act afterwards.

Iterating Based on Feedback

Feedback is only valuable once it has been triaged. A group typically receives twenty to forty comments and has limited time; treating them as an undifferentiated queue means the team spends an hour adjusting a shadow while a broken link remains broken. Sort every comment into severity bands before touching the file:

Band Definition Examples Action
Critical — blocking Prevents an evaluator from completing the stated task Dead-end frame; modal with no close; wrong or missing prototype start frame; link permissions wrong Fix immediately, before anything else
Major — comprehension Task is completable but the user is confused or misled Unclear icon-only action; primary CTA not distinguishable; misleading transition direction; placeholder copy on a core screen Fix after all critical items
Minor — polish Cosmetic inconsistency that does not impede use 4px spacing drift; two near-identical greys; inconsistent corner radius; icon optical alignment Fix if time allows; batch by style or component
Out of scope / won't fix Valid but outside the brief or this iteration "Add dark mode"; "build the payment flow"; conflicting taste preferences Record with a one-line rationale; do not silently ignore

The sequencing rule is non-negotiable: repair broken prototype connections before any visual refinement. There are two reasons. First, a navigable but plain prototype demonstrates the skill being assessed — simulating realistic user interaction — whereas a beautiful dead end demonstrates nothing. Second, visual refinement can itself break connections: replacing a hand-drawn button with a component instance, or restructuring a frame into auto-layout, detaches or relocates the hotspot the connection was attached to. Fix flow, verify flow, then style, then verify flow again.

Work through the critical band in one pass with a single person driving while the inventory's exit-point column is open beside them, because that column is the definitive list of connections that must exist. Then re-run the full critical path in presentation mode. Only when the path is clean should the team move to major and minor items, assigning them back to the owner of the relevant page so that ownership discipline survives the revision phase. Minor cosmetic issues are usually best fixed at the component or style level rather than screen by screen: if the grey is wrong, correct the published colour style once and every instance follows.

Throughout, document what changed and why. A change log serves three purposes: it demonstrates to evaluators that their feedback was taken seriously, it prevents the same issue being raised twice, and it supplies the evidence base for the reflective component that most academic submissions require. Keep it in the Figma file on the Team page, or in the submission document, in a simple tabular form:

# Feedback received (source) Severity Decision and change made Owner Status
1 "Back chevron on 03-Class Detail does nothing" (Group B, pinned comment) Critical Connected chevron to 02-Class List with "Move out" transition; audited all other back icons and connected four more Jonah Done — comment resolved
2 "Couldn't tell which button was the main action on Home" (Group B) Major Applied Button/Primary variant to "Browse classes", Button/Secondary to "My bookings"; updated component variant list Priya Done
3 "Success screen uses lorem ipsum" (Group B) Major Replaced with real booking summary copy including class name, time and studio address Amina Done
4 "Card shadows inconsistent between flows" (self-QA) Minor Created shared effect style Elevation/Card and applied to the Card master component Priya Done
5 "Add a dark mode" (Group B) Out of scope Noted as a future iteration; not required by the brief and not achievable in remaining time Team Deferred — rationale recorded

Deciding not to act is a legitimate outcome, provided the rationale is written down. Evaluators are not always right: a comment may reflect an unfamiliarity with the platform's conventions, or may conflict with another evaluator's comment. Record the conflict and the reasoning ("Group B wanted the filter above the list, Group C below; retained above to match iOS convention and the pattern used on 02"). This is exactly the kind of justified design judgement that assessment rubrics reward.

Close the loop properly. Once revisions are complete, resolve each addressed comment in Figma — ideally with a one-line reply saying what was done — then run the incognito link test again, because permissions and start frames can be disturbed by file reorganisation. Finally, re-share the updated link and notify the evaluators that a revised version is available, pointing them to the change log and, if useful, to the specific flows you would like them to re-check. Re-notification matters: an evaluator who is never told their comment was actioned has no way to validate the fix, and a second quick pass often catches a change that solved one problem while creating another. For submission, hand in the prototype link with comment access enabled, confirm the named flows and start frame are correct, and attach the screen inventory and change log as evidence of process — the artefacts that show not only what the team built, but how it was built, verified and improved.
