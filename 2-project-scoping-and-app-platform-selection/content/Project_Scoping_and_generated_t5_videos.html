Introduction

The Windows desktop remains one of the most widely deployed application platforms in business, education, and engineering settings. Unlike a phone, a Windows machine typically assumes a large screen, a mouse or trackpad, a full keyboard, multiple overlapping windows, and long working sessions. Those assumptions shape everything from how much information you can place on a screen at once, to how you expose commands (menus, ribbons, toolbars, right-click context menus, keyboard shortcuts), to how users expect to move data between applications.

In this module you are deciding which platform fits your project. Windows is a strong choice when users need dense data views, precise pointer input, file system access, long-form content creation, or integration with an organization's existing productivity and identity systems. It is a weaker choice when your users are mobile, occasional, or touch-first. The constraints matter as much as the capabilities: varying screen sizes and DPI settings, accessibility and keyboard navigation expectations, installation and update paths, and the strong conventions users already carry from Office and other Windows software.

The videos below approach Windows from three angles: the Microsoft 365 ecosystem that many Windows users live inside, the current developer tooling story on Windows, and a low-code route to building Windows-friendly business apps. While watching, note the interaction patterns you see repeatedly (ribbons, panes, command bars, keyboard shortcuts), and ask yourself what each one assumes about the user's hardware, attention, and environment. Those observations are the raw material for the platform justification and scope document you will write.

How These Videos Support the Learning Outcomes

Together these videos let you characterize the Windows side of the mobile/web/desktop comparison called for in MO1: you see the input assumptions, screen density, and interaction conventions of desktop productivity software, plus the cloud and web counterparts that blur the line. The developer experience and Power Apps videos surface practical build-and-deploy considerations - tooling, low-code versus custom development, organizational integration - that you will need to cite when you select and justify a platform under MO2. Finally, the constraints you identify while watching (hardware assumptions, licensing and ecosystem dependencies, development effort) translate directly into the objectives, constraints, and success criteria sections of the scope document required by MO3.
