Semester Group Project — Phase 2

Requirements Gathering, Stakeholder Analysis, and Use Case Development

Module: Use Case Scenarios

Assignment Type: Semester Group Project — Phase 2 of an ongoing series

Estimated Student Effort: 2–4 hours (group effort; divide and coordinate tasks among members)

Builds On: Phase 1 — Project Proposal and System Vision Document

Feeds Into: Phase 3 — System Design and Prototyping

Transparency in Learning and Teaching (TILT)

Purpose — Why This Assignment Matters

In real software development projects, the single most expensive class of mistake is a misunderstood or missing requirement discovered late in development. This assignment gives your team the structured practice of doing requirements engineering the right way: identifying every person or group affected by your software, systematically cataloguing every action the software must support, and describing those actions in enough detail that a developer, a tester, and a non-technical stakeholder can all read the same document and arrive at the same understanding.

The deliverables you produce here — your stakeholder register, your complete action inventory, your use case scenarios, and your task analyses — become the authoritative specification for your project. Every design decision, every feature, and every test case in later phases will trace back to what you write here. Doing this work carefully now saves significant rework later and directly mirrors professional practice in software engineering, business analysis, and UX design.

Task — What You Will Do

Your team will systematically identify all stakeholders and user roles for your project application, enumerate every action that can be performed within the software, and produce a complete Use Case Scenario and Task Analysis for each action. Detailed instructions are provided in the Task Description section below.

Criteria — How You Will Be Graded

Your submission is evaluated on the completeness of your stakeholder analysis, the coverage and accuracy of your action inventory, the structural correctness and clarity of each use case scenario, the quality of each task analysis, and the overall professional presentation of the document. A detailed rubric is provided at the end of this assignment.

Learning Outcomes

Upon successful completion of this assignment, you will be able to:

  1. Identify and classify all stakeholders and user roles for a software system using structured stakeholder analysis techniques, distinguishing between users and non-user stakeholders and mapping roles to system permissions.
  2. Enumerate the complete set of actions a software application must support, including common cross-application functions, core application-specific functions, and edge-case interactions, using systematic coverage techniques.
  3. Construct well-formed Use Case Scenarios for each identified action using a consistent template that includes actor, preconditions, main success scenario, alternative flows, exception flows, and postconditions.
  4. Produce a Hierarchical Task Analysis (HTA) for each action that decomposes user goals into observable sub-tasks and decision points, and map those sub-tasks to the corresponding use case flows.

Background and Context

This is Phase 2 of your semester-long group project. In Phase 1, your team defined a project concept, identified the problem your software addresses, and articulated a high-level system vision. You should refer to your Phase 1 deliverable throughout this assignment; your stakeholder analysis and action inventory must be consistent with the system vision you already established.

This phase is the most detail-intensive requirements engineering effort in the project. The work you produce here is not a throwaway exercise — it becomes the living specification document your team updates and references through all remaining phases.

Key Terms and Definitions

The following terms are used throughout this assignment. Make sure every team member is familiar with them before beginning work.

Stakeholder

Any individual, group, or organization that has an interest in or is affected by the software system, whether or not they directly interact with it.

Actor

A role that interacts directly with the system. In use case notation, actors represent roles rather than specific individuals. One person may play multiple actor roles.

Use Case Scenario

A narrative description of how an actor interacts with a system to achieve a specific goal. It captures the sequence of steps, decisions, and outcomes involved in a single interaction path.

Main Success Scenario

The ideal interaction path where everything proceeds as expected and the user achieves their goal without errors or exceptions. Written as a numbered sequence of actor and system actions
